## 2. Flag enforcement (FR-PLT-001 slice for `layer2`)
- **Database:** `platform_settings['flag.layer2']` (default `false`, audited changes through staff action `flag.set`). `public.l2_enabled()` reads it. **Entry paths only (PR #10 review round 3, finding 4):** `perform public.l2_assert_enabled()` (→ raises `layer2_disabled`) starts every function that **starts** something new — `submit_pool`, `review_pool`, `execute_collection_mechanism`, `launch_pool`, `reserve_investment`, `submit_pool_tranche_evidence`, `verify_pool_tranche`, statement upload, `commit_distribution_run`, the mock deposit trigger and the other flag-dependent staff actions (§9). **Completion paths never check the flag**, so money already in flight always finishes, investors keep their rights and the books stay true while the flag is off: **`cancel_investment`** (cancelling an existing commitment until 48 hours before the deadline is the investor's 17 CFR 227.304(a) right, not new activity — PR #10 review round 5, finding 3), **`set_collection_state`** (staff can still move a Pool that is already in `DEFAULT` or `REMEDIATION` — round 5, finding 4), `mark_investment_funding`, `record_investment_funded`, `record_stray_fund_move`, `record_stray_fund_refund_confirmed`, `record_investment_returned`, `record_investment_refunded`, reservation expiry (§4.3), `settle_pool`, `mature_due_pools`, `record_pool_tranche_released`, `record_collection_deposit`, `reconcile_pool_revenue`, `record_pool_payout_confirmed`, the `pool_ops` runner and its confirmations, the `regcf.*` webhook route and inbox branch, and L2 recon (§5.1).
- **Turning the flag off (round 3, finding 4 — rule chosen: allow, never block):** `flag.set off` is always accepted, even while a Pool is live or holds escrow, collection cash or open `pool_ops`. Off means **no new Layer 2 activity**: fan and creator routes return 404 `layer2_disabled` and the entry functions above refuse. Everything already started keeps running with the flag off: the worker still expires reservations, settles Pools at their deadline (target-or-refund), matures Pools, runs `pool_ops` (refunds, disbursements of tranches already verified, payouts of runs already committed, `close_offering`), reconciles revenue and runs L2 recon; webhooks are still accepted and processed. Staff keep the Pool money view, queue and recon (§9). **Cancellation stays open with the flag off (round 5, finding 3; replaces the round-3 note that investors couldn't cancel until the flag was back on):** `POST /investments/:id/cancel` and the investor's own `GET /investments/:id` sit outside the flag gate (investor auth + `REGCF_PROVIDER=mock`, like the other completion routes), the holding page shows a cancel-only view of an open investment while the server flag is off, and the §4.3 resolution of a `cancel_pending` row runs in the worker regardless. **Collection state with the flag off (round 5, finding 4 — option chosen: pause adverse moves, keep staff moves):** `reconcile_pool_revenue` keeps reconciling cash and still cures `AT_RISK → COLLECTING`, but makes **no adverse transition** (`COLLECTING → AT_RISK`, `AT_RISK → DEFAULT`) while `l2_enabled()` is false, so no new default arises while the creator can't upload statements; the next run with the flag on applies them as of its `now`, measured from the stored `collection_state_since` (a Pool `AT_RISK` throughout may move to `DEFAULT` on that run). The staff `pool.collection_state` action (`set_collection_state`) runs regardless, so a Pool already in `DEFAULT` or `REMEDIATION` can still be moved (§6, §9). The mock deposit trigger stays an entry path (real deposits arrive by webhook, which runs anyway). Refusing `off` while money is held was rejected: it would let a stuck op keep the flag on indefinitely and gives no extra safety, since the completion paths are flag-independent anyway.
- **API:** Layer 2 fan, creator and flag-dependent staff route plugins register a `preHandler` that returns 404 `layer2_disabled` unless `REGCF_PROVIDER=mock` **and** the DB flag is on; the `regcf` webhook route, the staff read/recon routes and the staff collection-state route (§9), the investor's cancel route and own-investment read (above) and the worker's Layer 2 steps require `REGCF_PROVIDER=mock` only (completion paths, above). `REGCF_PROVIDER=mock` is refused at startup in a deployed environment (same rule as the M1 sandbox), so Layer 2 can't be on in production by construction. **One route is outside the gate (PR #10 review round 2, finding 5):** the flag switch itself, `POST /api/v1/staff/flags/layer2` in the M1 staff plugin (`apps/api/src/routes/staff.ts`) — it can't sit behind the gate it opens. It is gated only by staff role + **aal2** + `privileged()` (action `flag.set`: typed reason, audit, single-operator rules), and turning the flag on is refused with `409 provider_missing` unless the API runs with `REGCF_PROVIDER=mock` — which it never does deployed.
- **Web:** `/v1/config` reports `flags.layer2` from the server. Layer 2 pages that read data render the "isn't open yet" state when the API says `layer2_disabled`; the client `?flags=` override only reveals mock-only screens, never data. **Production builds (PR #10 review round 2, finding 6):** in a production web build (`import.meta.env.PROD`) `useFlag('layer2')` is the server's `flags.layer2` only — the `?flags=layer2` override, its sessionStorage copy and `VITE_FLAG_LAYER2` are ignored for `layer2` — so a shared `?flags=layer2` link can't show Layer 2 screens from a deployed site (E1 readiness condition 1). The override keeps working in the Vite dev server (`pnpm dev`) for reviewing mock-only screens; screenshots of gated pages use the dev server or a local API with the server flag on. Every `layer2` route renders `Layer2DemoBanner` (inside `FeatureRoute`).

**Investments** state machine: `reserved → funding → funded → issued`; `reserved → expired | cancelled`; `reserved → returned` (a dead or cancel-pending reservation whose provider refs were stored by the §4.3 lookup and whose fund move is then returned — round 4, finding 3); `funding → returned`; `funded → refund_pending → refunded`; `funding → refund_pending` (fund move settles on a cancellation-pending investment, below); `reserved | funding | expired | cancelled → refund_pending` (a first fund move that can't be applied, §3.1, or a cancel-pending reservation whose fund move settles, §3 Cancellation). Pools gain `issuer_other_regcf_12m_minor` + `issuer_other_regcf_attested_at` (§4.1; round 3). **Counted reservation (PR #10 review round 4, finding 1 — the one definition every rule below uses):** `status = 'reserved' and (reserve_expires_at > now or provider_call_started_at is not null)`. A reservation with a provider call started may have moved money at the provider, so its headroom and Units stay counted past expiry, through the expiry-lookup grace and while its fund move is pending; it leaves the count **only** when the §4.3 resolution (expiry or cancel) or a §3.1 confirmation moves it to a terminal state (`expired`, `cancelled`, `returned`) or another counted state (`refund_pending`, `funded`). **Settlement doesn't take it out either** (§5 Settlement; PR #10 review round 5, finding 1). `provider_call_started_at` is set only by a conditional update (`where status = 'reserved' and cancel_requested_at is null and reserve_expires_at > now` and the Pool `live` before `ends_at`), so a reservation that has left the count can never re-enter it through a provider call. Limit usage counts **counted reservations**, `funding`, `funded`, `issued`, `refund_pending` (same list as FR-L2-INV-003; finding 10).
**Cancellation (PR #10 review round 2, finding 1; replaces the round-1 refusal in `funding`):** `cancel_investment(inv, user, now)` judges the 48-hour cut-off at **request time** and, before it: `reserved` **with `provider_call_started_at` null** → `cancelled` at once (Units back, headroom freed, notice "nothing was charged"); **`reserved` with `provider_call_started_at` set (PR #10 review round 4, finding 2)** — a trade or fund move may exist at the provider — **accepted and recorded**: sets `cancel_requested_at = now` (status stays `reserved`, still a counted reservation), returns `'cancel_pending'` ("Cancellation received — if any payment was taken it will be refunded in full"), and the §4.3 resolution settles it: no trade or the trade voided with `cancelTrade` → `cancelled` (Units and headroom released in that transaction) + notice "nothing was charged"; a fund move exists → refs stored, and when the fund move settles `record_investment_funded`'s cancellation-pending path moves it to `refund_pending` (`cancelled_by_investor`) with a refund op and a notice for the **received** amount; returned → `returned`. The cancel and the purchase's `provider_call_started_at` update serialise on the investment row lock (pool → investment), so either the cancel sees no call and cancels at once (the purchase's conditional update then matches nothing and makes no provider call) or it sees the call and goes pending; `funded → refund_pending` (refund op for `funded_received_minor`); **`funding`: accepted and recorded** — sets `cancel_requested_at = now` (status stays `funding`), returns `'cancel_pending'` (API 200 `{ result: 'cancel_pending' }`; the fan sees "Cancellation received — we'll refund your payment in full as soon as it arrives"); a repeat request returns `'cancel_pending'` again. Then: `record_investment_funded` on an investment with `cancel_requested_at` set **never makes it `funded`** — it posts the fund move as received, sets `funded_received_minor`, moves it straight to `refund_pending` (`status_reason = 'cancelled_by_investor'`) and queues the full refund op, whenever the fund move settles (after the cut-off, after the deadline, after settlement); `record_investment_returned` simply closes it as `returned` (no money arrived). `settle_pool` never issues a cancellation-pending investment (it issues only `funded`). We never refund money that hasn't arrived; the investor's right to cancel is fixed when they ask.
**Counter rule (M1 §3.5, as on `main`):** `pools.raised_minor` and `investors_count` count only `funded` (and, after close, `issued`) investments; `units_committed` also counts **counted reservations** and `funding` (round 4, finding 1). The stored counter changes only inside the functions below, so a `reserved` row whose expiry passed with no provider call stays in it until the expiry step expires it (conservative: Units are never sold twice). Every function that moves an investment out of a counted state (`cancel_investment` (immediate path), the §4.3 resolution (`expired`, `cancelled`), the failed branch of `settle_pool` (`funded → refund_pending`; settlement itself expires only uncounted reservations — round 5, finding 1), `record_investment_returned` (`funding → returned` and `reserved → returned` — Units out of `units_committed` and the headroom freed in that transaction; round 4, finding 3), and `record_investment_funded` on its cancellation-pending and unapplied paths — `funding`/`reserved` → `refund_pending` releases `units_committed` and never adds to `raised_minor`/`investors_count`) adjusts the counters **in the same transaction**, never at refund confirmation. A stray fund move (§3.1) changes no counter. `settle_pool`'s funded branch issues **only `funded`** investments; `refund_pending` ones finish refunding from escrow through their op and are never part of the amount closed to the issuer.

### 3.1 Matching a fund move; fund moves we can't apply (PR #10 review round 2, finding 3; follows M1 §3.5.1)
A fund move is money in the offering escrow; once the provider says it settled, it is posted — every time, exactly once — and either applied to one investment or refunded in full from what actually arrived. As M1 §3.5.1 does for captures:
1. **Match by fund ref first:** the investment whose `provider_fund_ref` equals the event's fund move id.
2. **Else by the fund move's `externalId`** (our investment id), only if that investment's `provider_fund_ref` is null (the webhook beat `mark_investment_funding`) or equal.
3. **Same fund move again** → idempotency key `fund:<fund_ref>` already posted → `'duplicate'`, nothing moves (lock-then-check, §4.2).
4. **Stray fund move** — one that names an investment whose `provider_fund_ref` is a *different* ref, or an investment that already had a fund move applied (`funded`, `issued`, `refund_pending`, `refunded`, `returned`), or that names no investment but carries our offering: `record_stray_fund_move(pool, fund_ref, amount)` posts `investment.funded_stray` (+`pool_escrow` / −`pool_investor_liability`, `external_ref = fund_ref`, idempotency key `fund:<fund_ref>`), changes **no investment state and no counter**, and creates **its own refund op keyed by the fund ref**: `pool_ops(kind 'refund', subject_id = the provider_events row id, fund_ref, amount_minor = received amount, idempotency_key = refund:fund:<fund_ref>)`. Its confirmation, `record_stray_fund_refund_confirmed(fund_ref, refund_ref, amount, idem)`, checks the amount against the stray and posts `investment.stray_refunded` (reverse legs). Alert log `fund_move.stray`; the op shows in the staff Pool money view. An open stray (refund not confirmed) counts in expected escrow and liability (§3, §5.1); one whose refund op is unconfirmed past `recon.maxBreakAgeBusinessDays` opens a `stray_fund_move_aged` break.
5. A fund move matching no investment and no offering stays `unmatched` in the inbox for staff (M1 §5).

**`record_investment_funded(inv, fund_ref, amount, idem, now)`** (steps 1–3 matched it to `inv`): locks pool → investment, then checks `idem`; re-checks under the lock that the investment's `provider_fund_ref` is null or `fund_ref` and that no fund move was applied to it yet — otherwise returns `'stray'` and the caller hands the event to `record_stray_fund_move`. It always stores `funded_received_minor = amount` and `provider_fund_ref`, posts the fund move once (+escrow / −liability), then:
- **Applied** (`'applied'`) only when all hold: status `reserved` with `reserve_expires_at > now` or `funding`; no `cancel_requested_at`; Pool `live` (not yet settled — `settle_pool` runs at `ends_at` and waits up to `l2.settleGraceMinutes` for `funding` investments, so a fund move after settlement is late); `amount = amount_minor`. → `funded`, `raised_minor += amount`, investors recounted (counter rule).
- **Cancellation pending** (`'refund:cancelled_by_investor'`): `cancel_requested_at` set (status `funding`, or `reserved` with a provider call started — round 4, finding 2) → `refund_pending`, refund op for `amount`, Units out of `units_committed`, notice with the received amount (§3 Cancellation, §5.2).
- **Unapplied** (`'refund:<reason>'`, reasons `amount_mismatch`, `reservation_expired`, `reservation_cancelled`, `offering_closed`): status `reserved`/`funding`/`expired`/`cancelled` → `refund_pending` with the reason, refund op for the **received** `amount`; Units leave `units_committed` if they were still counted (`reserved`/`funding`), `raised_minor` never changes (counter rule). `amount_mismatch` also opens an `unapplied_funding` break (staff-resolved, pausing).
The refund op of an investment is `pool_ops(kind 'refund', subject_id = investment id, idempotency_key = refund:inv:<investment_id>)` (key scheme for every kind: §5 Outbound); `record_investment_refunded` requires `amount = funded_received_minor`. Uniqueness of `pool_ops` is the **idempotency key alone** (no `unique(kind, subject_id)`), so an investment refund and a stray refund on the same Pool never collide, and a second refund for one investment can only arise from a second key — which this section never creates.

**`record_investment_returned(inv, fund_ref, code)`** (PR #10 review round 5, finding 5) stores `provider_fund_ref = coalesce(provider_fund_ref, fund_ref)` — as `record_investment_funded` does — in the transaction that moves it to `returned`, so a return whose webhook beat `mark_investment_funding` (or whose ref no lookup stored) still leaves the investment carrying the fund ref, and §5.1 always matches the provider's returned fund move to it.

## 4. Concurrency: the investment limit (01a §3, AC-I1/I2/I5)
`reserve_investment` runs in one transaction: lock `investor_profiles` row (`for update`) → lock `pools` row → check KYC, state, flag, deadline, self-investment, min Units, availability (`units_committed + n ≤ units_total`), **issuer cap** (`committed amount + n × price ≤ issuer_cap_remaining_minor`, else `issuer_cap_reached`, §4.1) → usage = Σ amount of the investor's **counted reservations** + `funding` + `funded` + `issued` + `refund_pending` investments created in the trailing 12 months + self-reported elsewhere (`regcf_usage`; round 4, finding 1 — a reservation with a provider call started counts past its expiry) → refuse `regcf_limit_exceeded` if usage + amount > limit → insert `reserved` with `reserve_expires_at = now() + l2.reserveMinutes`. The investor lock serialises one person's purchases across all offerings, so N concurrent purchases admit exactly those that fit. Expiry (worker, §4.3) and returned fund moves free the headroom (AC-I2) — expiry only once no provider trade for the reservation can still take money (round 3, finding 1), so a freed headroom is never re-consumed by a late fund move. **Until then the row is a counted reservation (§3; round 4, finding 1):** after a crash past `fundTrade` the reservation expires by time, but `provider_call_started_at` keeps it in `regcf_usage`, so a new reservation that would take usage past the limit is refused `regcf_limit_exceeded` during the grace and while the fund move is pending. The limit formula and thresholds live in `packages/shared/src/policy.ts` (`regCf`) and are mirrored in `platform_settings['regcf_limits']` (sync test).

### 4.1 Issuer cap (PR #10 review, finding 1)
Remaining 12-month cap for a creator = tier cap (`tier_limits.reg_cf_cap_minor` of the Pool's artist, never above `POLICY.regCf.issuerCapMinor`) − Σ over the creator's **other** Pools of `raised_minor` for those closed (`funded`/`matured`) in the trailing 12 months and `max_minor` for those `in_review`/`approved`/`live`. **"The creator" is the owner (PR #10 review round 4, finding 5):** on `main` one profile can own several artist rows (`artists.owner_id`, not unique), and they are one issuer, so the sum runs over the Pools of **every artist with the Pool's `owner_id`** (option chosen over "one artist per owner for Layer 2": same lock cost, no new product restriction). `submit_pool` and `launch_pool` both read the Pool's `artist_id` → `owner_id` unlocked, lock **all of that owner's artist rows in id order** (`select … from artists where owner_id = $1 order by id for update`), then the Pool, and refuse `tier_cap_exceeded` when this Pool's **`max_minor`** (Units × price) exceeds the remaining cap; `launch_pool` writes the remaining cap it checked to `pools.issuer_cap_remaining_minor`. **Issuer-side sales outside FanZuP (PR #10 review round 3, finding 5):** 17 CFR 227.100(a)(1) aggregates **every** §4(a)(6) sale by the issuer in the 12 months before the sale, and 227.100(c) counts entities controlled by or under common control with the issuer and its predecessors (SEC issuer guidance; other exempt, non-crowdfunding offerings are not aggregated). FanZuP sees only its own Pools, so the creator attests a figure: `pools.issuer_other_regcf_12m_minor` (≥ 0, Reg CF sales in the preceding 12 months by the creator, its affiliates under 227.100(c) and predecessors, on any other platform) with `issuer_other_regcf_attested_at`, captured by `submit_pool` and **re-attested at launch** (the launch request carries the current figure; `launch_pool` stores it and uses it). The remaining cap is then: tier cap − that figure − the FanZuP sum above. Who counts as "the issuer" (artist, label, the vehicle of L2-Q2) and whether an attestation is enough is counsel item **L2-Q12** (tied to L2-Q2; the owner-level aggregation above is the demo's floor); the demo labels the field "self-reported, pending counsel".
**Reservation backstop (round 3, finding 10 — a defensive invariant):** `reserve_investment` refuses (`issuer_cap_reached`) a reservation that would take Σ amount of the Pool's counted reservations + `funding` + `funded` investments past `issuer_cap_remaining_minor`. Because `launch_pool` already checked `max_minor ≤ issuer_cap_remaining_minor` and nothing sells past `max_minor` (Units availability), this can't refuse anything today; it is kept as an invariant check so a future change (a recomputed cap, a raised maximum) can never sell past the cap silently. A test asserts it by lowering `issuer_cap_remaining_minor` directly.

### 4.2 Lock order (aligned with M1 §3.5.1 on `main`)
Every Layer 2 money function locks in the order **investor profile → artist(s) (all of the owner's, in id order — §4.1) → pool → investment(s) → pool tranche / distribution payout**, and takes only the suffix it needs. Functions that start from an investment, tranche or payout id read its `pool_id` unlocked (it never changes), lock the pool, then the row — the order `settle_pool` and `commit_distribution_run` use — so a fund-move webhook, a cancellation or a refund confirmation racing the deadline can't deadlock with settlement. **Lock, then check:** functions keyed by a ledger idempotency key (`record_investment_funded`, `record_investment_refunded`, `record_pool_tranche_released`, `record_pool_payout_confirmed`) take their locks **before** checking for the key, so two processors racing on one event serialise: one posts, the other returns `'duplicate'`. `record_stray_fund_move` and `record_stray_fund_refund_confirmed` serialise on an advisory lock keyed by the fund ref, after the pool lock (M1 §3.5.1). Reservation expiry locks per Pool (pool, then its expired reservations), not investment-first.
**One clock (PR #10 final review):** every Layer 2 money function takes `p_now` (the worker's or request's clock) and decides liveness, expiry, the cancel cut-off, settlement grace, period windows and the 12-month windows from it — never from `now()` or the transaction time — so the API, the worker and tests evaluate one instant consistently (timestamps written as bookkeeping defaults aside).

### 4.3 Reservation expiry (PR #10 review round 3, finding 1; follows M1 §3.4 / §5 "Hold expiry")
A dead or cancel-pending reservation's limit headroom and Units are freed **only when no provider trade for it can still take money** — M1's rule that a hold is released only after the provider confirms the payment attempt is cancelled. Until then it is a **counted reservation** (§3; round 4, finding 1). The worker step (`expireReservations` in the API, then the SQL `expire_investment_reservations(pool, ids, now)`, both flag-independent, §2) takes `reserved` investments whose `reserve_expires_at <= now`, whose Pool is no longer `live`, **or with `cancel_requested_at` set (round 4, finding 2)** — **excluding those whose `provider_fund_ref` is already stored** (a previous lookup found their fund move; they await its settle/return event through §3.1 and are not looked up again — round 4, finding 8; if that event never arrives, §5.1 ref matching opens `unmatched_provider_txn` for the fund move past the in-flight grace). The resolved terminal state is `cancelled` when `cancel_requested_at` is set, else `expired`:
1. **`provider_call_started_at` null** — no provider call was ever made → expire at once (`expired`, Units out of `units_committed`, headroom freed). (A cancel-pending row always has a call started — `cancel_investment` cancels the others at once.)
2. **`provider_call_started_at` set** — only once `l2.expiryLookupGraceMinutes` (5) past expiry, or past `cancel_requested_at` for a cancel-pending row (so an in-progress purchase request finishes first), **look up, never create**: `findTrade({ externalId: investment_id })` (the provider's lookup by our id — the trade was created with key `trade:<investment_id>` and `externalId = investment_id` — then `getTrade` for its fund moves):
   - **no trade** → expire (or cancel; notice "nothing was charged");
   - **trade with no fund move** → `cancelTrade(trade, key cancel_trade:<investment_id>)`; once the provider confirms it cancelled, expire (or cancel; notice "nothing was charged"). If the cancel is refused because a fund move appeared meanwhile (`trade_funded`), fall through to the next case;
   - **trade with a fund move** → don't expire: store the trade and fund refs on the investment (`record_investment_provider_refs`, status unchanged, still a counted reservation) and leave it to §3.1 (if the provider already reports the fund move settled, hand its object to the §3.1 matcher, idempotent on `fund:<fund_ref>`) — when the fund move settles, `record_investment_funded` treats it as cancellation-pending (`cancel_requested_at` set: `refund_pending`, `cancelled_by_investor`, notice with the received amount) or unapplied (`reservation_expired`, or `offering_closed` if the Pool settled) and refunds the received amount in full; if it's returned, `record_investment_returned` moves it **`reserved → returned`** (round 4, finding 3: Units out of `units_committed` and the headroom freed in that transaction — the only way such a row leaves the count without a refund). The headroom stays used until then (after settlement it is `refund_pending`, still counted until the refund confirms).
3. Expiry never calls `fundTrade`. The status change, the `units_committed` release and the audit row run in one transaction under the pool lock (§4.2), re-checking the investment is still `reserved` with the same `provider_trade_ref`/`provider_fund_ref` it had at lookup; on a `failed` Pool the same transaction runs `l2_maybe_mark_refunded` (§3; round 5). Rows on a settled Pool reach this step because their Pool is no longer `live` (§5 Settlement).
So limit usage can't exceed the investor's limit through a dead or cancelled reservation: it stays a counted reservation (§3) until the provider confirms there is no trade or a voided trade (after which no fund move for it can exist) or its fund move is returned; a settled fund move turns it into `refund_pending`, which is counted until the refund confirms.

## 5. Provider boundary and flows (ADR-007)
`RegCfProvider` (TransactAPI-shaped): `createIssuer`, `createOffering`, `updateOfferingStatus`, `createParty`, `setPartyKyc`, `createAccount`, `createLink`, `createTrade`, `fundTrade` (fund move into escrow), `getTrade` (trade + its fund moves), `findTrade({ externalId })` (lookup by our investment id; round 3), `cancelTrade` (void a trade with no fund move; refused `trade_funded` otherwise; round 3), `listTransactions({ offeringId | collectionAccountId, since })` (every escrow and collection-account movement with its id, kind, amount and `externalId`, for §5.1 ref matching; round 3), `getEscrow`, `closeOffering`, `disburseToIssuer`, `refundTrade`, `createCollectionAccount`, `getCollectionAccount`, `payoutFromCollection`, `simulateDeposit` (mock-only test trigger), `parseWebhook` (HMAC verify). Every mutating call carries an idempotency key derived from our row id, so a retry returns the original object (the two-phase op only needs "call again with the same key").

- **Launch:** API calls `createIssuer`/`createOffering`/`createCollectionAccount` (keys `issuer:<artist>`, `offering:<pool>`, `collection:<pool>`), then `launch_pool(refs)`, which re-checks the issuer cap on the maximum under the artist lock (§4.1) and requires `duration_days ≥ regCf.minOfferingDays`. Retry-safe. The provider offering's end date is derived from the stored Pool row (deterministic params, as M1 §4.4 step 3), so a retried launch replays the same objects.
- **Purchase:** `reserve_investment` → `createTrade` (key `trade:<investment>`) → `fundTrade` (key `fund:<investment>`) → `mark_investment_funding`. Fund move settles asynchronously → webhook `fund_move.settled` → `record_investment_funded`. Returned → `record_investment_returned`. **Idempotency-Key exactly as M1 §4.4 on `main`:** the `api_idempotency` claim (`investments:<user>:<key>`) and `reserve_investment` run in **one transaction** (reservation under a savepoint); a rule violation (`regcf_limit_exceeded`, `pool_sold_out`, `issuer_cap_reached`, `kyc_required`, …) rolls back to the savepoint and is **stored on the claim as `done` with its 4xx response**, so a retry replays it; the 2-minute abandoned-claim rule is the backstop; before every provider call (first pass and resume) a **resume guard** re-reads the investment (PR #10 review round 2, finding 2 — in Layer 2 `fundTrade` moves money at the provider, so a crash after the fund move but before the claim is stored `done` must not turn a purchase into "expired"): (a) the purchase's fund move was or will be applied — `funding` with no `cancel_requested_at`, `funded`, `issued`, or `refund_pending`/`refunded` **with `funded_at` set** (the fund move was applied — `funded_at` is set only on the applied path — and the refund came later from an investor cancellation of a `funded` investment or a failed Pool) → store and return the **success** response (201 `{ investmentId, status: <current>, amountMinor, units }`), no provider call; **(a′) money arrived or may arrive but is never applied (PR #10 review round 4, finding 7)** — `refund_pending`/`refunded` with `funded_at` null (an unapplied fund move, §3.1, or a cancellation pending when it arrived) → the stored 409 the dead-reservation path gives, with `{ refundPending: true }`: `status_reason` `cancelled_by_investor` or `reservation_cancelled` → `409 investment_cancelled`; `reservation_expired` or `offering_closed` → `409 reservation_expired`; `amount_mismatch` → `409 payment_not_applied`. So a crashed purchase whose fund move is unapplied gets the same answer whether the retry comes before the fund move settles (case (e)) or after (a′); likewise `funding` or `reserved` **with `cancel_requested_at`** → stored `409 investment_cancelled` (`refundPending: true` when a fund ref exists or a provider call started), no provider call; (b) `expired` → terminal stored `409 reservation_expired`; `cancelled` → terminal stored `409 investment_cancelled` (round 4); `returned` → terminal stored `409 funding_returned` ("Your bank returned the payment. Start again from the Pool page."); (c) `reserved`, unexpired, no `cancel_requested_at`, Pool `live` before `ends_at` → set `provider_call_started_at` by the conditional update of §3 (committed before the first call, M1 `call_started_at` pattern; if it matches no row, re-run the guard) and call the provider — the guard runs again before `fundTrade`, so a reservation that died after `createTrade` gets case (e), never a first `fundTrade`; (d) `reserved` but dead (expired time or Pool not live) **and `provider_call_started_at` null** → terminal stored `409 reservation_expired`, no provider call; (e) `reserved` but dead **with `provider_call_started_at` set** (a crash between the calls and `mark_investment_funding`, or the reservation died between the calls) — **look up only, never create or fund (PR #10 review round 3, finding 1; M1 §4.4: no payment is created for a dead hold, and the attempt is cancelled at the provider)**: `findTrade({ externalId: investment_id })` / `getTrade`, exactly as reservation expiry does (§4.3): no trade → stored `409 reservation_expired`; a trade with no fund move → `cancelTrade` (key `cancel_trade:<investment_id>`), then stored `409 reservation_expired`; a trade **with** a fund move → `record_investment_provider_refs` stores the refs (status unchanged) and the fund move is recorded only through §3.1 (its webhook — or, if the provider already reports it settled, the guard hands the provider's fund-move object to the same §3.1 matcher, idempotent on `fund:<fund_ref>`), which treats it as unapplied (`reservation_expired` / `offering_closed`) and refunds the received amount; the stored response is `409 reservation_expired` with `{ refundPending: true }` ("This reservation expired. Any payment taken will be refunded in full."). A first `fundTrade` call is **never** made for a dead reservation, so a replay can't move money or push limit usage over the cap. **`mark_investment_funding` re-checks the same conditions under the pool lock (round 3):** it moves `reserved → funding` only if the reservation is unexpired, has no `cancel_requested_at` (round 4) and the Pool is `live` before `ends_at` — and then queues the 227.303(d) commitment notice (§5.2; once per investment, round 5); otherwise, for a row still `reserved` but dead, it stores the refs only, leaves the status, and returns `'dead'` — the API then stores `409 reservation_expired` (`refundPending: true` when a fund ref exists), and the fund move is refunded on arrival (§3.1). **A row no longer `reserved` (PR #10 final review)** — the fund-move webhook or a cancellation got there first — gets its refs stored (coalesce) and the function returns its **current status** (`funding`, `funded`, `refund_pending`, `returned`, …), never `'dead'`, so the API answers it as resume-guard case (a)/(a′)/(b). **One liveness predicate:** `l2_reservation_live(investment, pool, now)` — `reserved`, `reserve_expires_at > now`, no `cancel_requested_at`, Pool `live` and `now < ends_at` — is the only test `mark_investment_funding` uses and the test the applied path of `record_investment_funded` uses for a `reserved` row (a `funding` row applies while the Pool is `live`, i.e. until settlement, whose grace waits for it). Every `createTrade`/`fundTrade` parameter is derived from the stored investment row, never the request.
- **Settlement:** worker `settle_pool(now)` after the deadline (waits up to `l2.settleGraceMinutes` for in-flight fund moves of `funding` investments). **Reservations at settlement (PR #10 review round 5, finding 1):** in its transaction `settle_pool` expires only `reserved` rows with `provider_call_started_at` **null** (no provider call was made, so nothing can arrive: `expired`, Units out, headroom freed). A `reserved` row with a provider call started is a **counted reservation** (§3) and stays one: settlement never changes its status, Units or headroom. The §4.3 step picks it up because its Pool is no longer `live` and resolves it — no trade or a voided trade → `expired` (`cancelled` if cancel-pending); a fund move → refs stored, and when it settles §3.1 treats it as unapplied (`offering_closed`, or `cancelled_by_investor` if cancel-pending) → `refund_pending`, refunded in full from the received amount; returned → `returned`. Funded → ledger close of Σ `funded` amounts, only `funded` investments issued (lock-up end = close + 12 months), tranche 1 verified, outbox `l2.op` close + disburse; **counted reservations and `funding` investments are never issued and never part of the amount closed** — they stay in `units_committed` until resolved (so Units issued + Units still committed never exceed `units_total`) and are refunded in full if money arrives. Failed → `refund_pending` + refund op (for `funded_received_minor`) for every funded investment, counters adjusted in the same transaction (counter rule, §3); **`units_committed` is recomputed as Σ Units of counted reservations + `funding`** (not `funding` only), so the §5.1 counter check stays exact; the Pool moves to `refunded` only by the §3 rule (`l2_maybe_mark_refunded`). A `funding` investment still in flight after the grace is not issued and not counted; when its fund move settles, the Pool is no longer `live`, so it is unapplied (`offering_closed`) and refunded in full (§3.1). The deadline is never less than 21 days after launch (`regCf.minOfferingDays`), so the earliest transmission to the issuer is at least 21 days after the offering information was posted (17 CFR 227.303(e)(3)(i)).
- **Outbound:** `pool_ops` (kinds `refund`, `disburse`, `payout`, `close_offering`), same states **and rules** as M1 `outbound_ops` on `main` (M1 §3.3, §5): the runner claims a due op with a lease **and a fresh `claim_token`**, and every outcome write (`sent`, `confirmed`, `failed`, `dead`, back to `initiated`) applies only `where claim_token = <ours>`, so a runner that outlived its lease can't overwrite the state of the one that re-claimed the op; `call_started_at` is set once, in the transaction just before the first provider call. `close_offering` confirms on the response; the others are `sent` until the webhook confirms; the SQL confirm function asserts the exact amount, and a provider amount that differs leaves the event failed (dead-letter) and opens an `amount_mismatch` break (§5.1).
  - **Idempotency keys (PR #10 review round 3, finding 7):** `pool_ops.idempotency_key` is unique and is also the key sent to the provider, so a key names exactly one money movement ever. One scheme for every kind, built only by `l2_queue_op` (and the stray path) from the subject id:

    | Kind | `subject_id` | `idempotency_key` | Guarantees |
    |---|---|---|---|
    | `refund` (investment) | investment id | `refund:inv:<investment_id>` | at most one refund per investment |
    | `refund` (stray fund move, §3.1) | `provider_events` row id | `refund:fund:<fund_ref>` | at most one refund per stray fund move |
    | `disburse` | tranche id | `disburse:<tranche_id>` | at most one disbursement per tranche |
    | `payout` | distribution payout id | `payout:<distribution_payout_id>` | at most one payout per distribution payout (investor, creator or platform line) |
    | `close_offering` | pool id | `close:<pool_id>` | the offering is closed once |

    Calls outside `pool_ops` use the same rule: purchase `trade:<investment_id>` / `fund:<investment_id>` and the reservation void `cancel_trade:<investment_id>` (§4.3, §5 Purchase); launch `issuer:<artist_id>` / `offering:<pool_id>` / `collection:<pool_id>`; the mock-only staff deposit trigger `deposit:<privileged_action_id>` (one deposit per staff action — the route never derives the key from amount and reference, so two real deposits with the same figures are never merged, and a retried action never deposits twice). `l2_queue_op` inserts `on conflict (idempotency_key) do nothing`, so re-queuing is harmless and a second movement for the same subject can only come from a different key — which only §3.1's stray path creates, by design.
  - **Never a stale amount; tranches in order:** a refund op's amount is fixed when the op is created: always what actually arrived (`funded_received_minor`, or the stray's received amount, §3.1). A `disburse` op's amount is `pool_tranche_release_amount()`, which depends on earlier releases (the last tranche is owed whatever `pool_issuer_payable` still holds), so: (1) a tranche's disburse op is created only when **every earlier tranche is `released`** — `verify_pool_tranche` queues it only then, and `record_pool_tranche_released` locks the next tranche and queues its op if it is already `verified`; (2) right before the first provider call the runner re-derives the amount and, in the transaction that sets `call_started_at`, updates the op if no call has started; (3) once `call_started_at` is set the amount is frozen — if what is owed later differs, the op fails `permanent` (`disburse_amount_changed`, alert) instead of sending the old figure. Distribution `payout` ops are fixed at commit (the run is immutable).
- **Webhooks:** `POST /api/v1/webhooks/regcf`, header `x-mock-escrow-signature: t=<unix>,v1=<hex hmac-sha256(secret, t + "." + rawBody)>`, 5-minute tolerance. Stored in `provider_events` (`provider='mock-escrow'`, unique event id) before processing; duplicate deliveries are no-ops; processing failures retry with the M1 inbox backoff. **Processing goes through the M1 inbox processor on `main` only** (M1 §3.2): every processor (inline attempt, worker, staff replay) claims the row (`processing`, `lease_until = now() + 5 min`, fresh `claim_token`) before work, and every outcome write — including the "wait for the matching row" path back to `received` — is conditional on `status = 'processing' and claim_token = <ours>`; Layer 2 adds a `regcf.*` branch to the dispatcher, never its own claim or status writes.

### 5.1 Layer 2 reconciliation and pause rule (aligned with M1 §7 on `main`)
- **Per Pool:** ledger `pool_escrow` vs provider escrow and ledger `pool_collection` vs provider collection balance. **In-flight allowance (M1 pattern):** amounts belonging to a `pool_ops` row still `sent`, or to a `regcf.*` event received less than `recon.inflightGraceMinutes` ago and not yet processed, are reported in the run's `inFlight` list and left out of the difference, so they open no break (AC-E1, finding 5). Past the grace they count.
- **Per-transaction ref matching (PR #10 review round 3, finding 2; M1 §7 "Matching"):** balances alone can hide two errors that cancel out, so each run also matches transactions, per Pool. Provider side: `listTransactions` for the Pool's offering escrow and collection account (fund moves, fund-move returns, refunds, disbursements, deposits, payouts). Ledger side: every Pool ledger transaction carrying an `external_ref` — `investment.funded` / `investment.funded_stray` (fund ref), `investment.refunded` / `investment.stray_refunded` (refund ref), tranche release (disbursement ref), `revenue.deposit` (deposit ref), payout confirmations (payout ref). Every provider transaction must match one ledger transaction by `external_ref` with the same amount, and every ledger transaction with an `external_ref` must match one provider transaction. A provider transaction with no ledger match opens **`unmatched_provider_txn`**; a ledger transaction with no provider match opens **`unmatched_ledger_txn`** (refs: Pool, ref, kind, amount; amount = the transaction's amount). The **in-flight allowance applies here too**: a provider transaction whose ref belongs to a `pool_ops` row still `sent`, or to a `regcf.*` event received less than `recon.inflightGraceMinutes` ago and not yet processed, is listed in `inFlight` and left out of matching; past the grace it is matched like any other. `close_offering` moves no money and has no ledger leg; a returned fund move never settled into escrow and has no posting, so it is matched to an investment `returned` with that fund ref instead (none → `unmatched_provider_txn`; `record_investment_returned` always stores the ref, §3.1, round 5). Both kinds are money kinds: **pausing** and derived (auto-resolve `cleared_by_run`), as in M1.
- **Counters and liability (PR #10 review round 2, finding 7; M1 §7 "Public counters"):** each run also checks, per Pool, `raised_minor` == Σ `amount_minor` of `funded` (+ `issued` after close) investments, `investors_count` == distinct investors among them, `units_committed` == Σ Units of **counted reservations** (§3) + `funding` + `funded` + `issued` (a cancellation-pending `reserved` or `funding` investment still counts until its resolution, or until its fund move settles or returns; round 4, finding 4). The worker runs L2 recon after the expiry step with the same `now`, so every `reserved` row it sees is counted; a `reserved` row that isn't (expired, no provider call, not yet expired by the step — e.g. a staff-triggered run between ticks) is listed in `inFlight` and opens no break; a difference opens `counter_mismatch` (not money, never pauses). And the ledger **liability**: credit balance of `pool_investor_liability` == Σ `funded_received_minor` of `funded` + `refund_pending` investments + Σ open stray fund moves (§3, §3.1); a difference opens `liability_mismatch` (amount = ledger − expected; money, pausing). Expected escrow and provider escrow both include open strays, so a stray in its refund window opens no break; past `recon.maxBreakAgeBusinessDays` unconfirmed it opens `stray_fund_move_aged`.
- **Confirmation amounts:** a `pool_ops` confirmation (refund, disbursement, payout) whose provider amount differs from the op is refused by the SQL confirm function; the processor opens an `amount_mismatch` break on the Pool (refs: op id, expected, provider amount) and the event goes to the dead-letter path. It stays open until staff resolve it, as in M1.
- **Breaks** live in `pool_breaks` (never `recon_breaks`), so Layer 2 activity can't move M1's per-campaign diff or its `PAYOUT_PAUSING_KINDS` (gate condition 1). **Layer 2 pausing kinds** (`L2_PAYOUT_PAUSING_KINDS`, next to M1's in `apps/api/src/recon.ts`): `escrow_diff`, `collection_diff`, `unmatched_provider_txn`, `unmatched_ledger_txn` (round 3, finding 2), `unapplied_funding`, `liability_mismatch`, `amount_mismatch`, `stray_fund_move_aged`. **Never pausing:** `counter_mismatch`, `revenue_shortfall`, `revenue_overage`, `refund_overdue` (§5.2 — refunds never pause, and pausing payouts wouldn't speed a refund up). An open one on a Pool with `|amount| > recon.materialityMinor` or older than `recon.maxBreakAgeBusinessDays` pauses **that Pool's** `disburse` and `payout` ops (left `initiated`, retried later); refunds never pause. `revenue_shortfall` and `revenue_overage` never pause: shortfall cash was never collected and overage stays in suspense, so neither can be distributed. Derived breaks (`escrow_diff`, `collection_diff`, `unmatched_provider_txn`, `unmatched_ledger_txn`, `counter_mismatch`, `liability_mismatch`, `stray_fund_move_aged`, `refund_overdue`) auto-resolve `cleared_by_run`; money-path breaks (`unapplied_funding`, `amount_mismatch`) stay open until staff resolve them, as M1's `amount_mismatch`.

### 5.2 Cancellation and failed-offering notices and refund timing (PR #10 review round 3, finding 6)
17 CFR 227.304(d): when an offering isn't completed, the **intermediary** must, within five business days, notify each investor of the cancellation, the reason and the refund amount expected, direct the refund of investor funds, and stop new commitments for the offering; 227.303(e)(3)(ii)–(iii) have the intermediary return funds when a commitment is cancelled under 227.304 or the offering isn't completed; 227.304(c) gives the same five-business-day notice-and-refund rule for commitments cancelled for lack of reconfirmation after a material change (not built, gate condition 10). In production these obligations sit with the intermediary (L2-Q3, L2-Q9); the demo performs them itself through the existing Layer 2 notices path (`l2.notify` outbox → `apps/api/src/l2/notices.ts`), never a second mechanism:
- **Failed Pool:** `settle_pool`'s failed branch, in its transaction, moves the Pool out of `live` (no new commitments: `reserve_investment` requires `live`), creates every refund op (key `refund:inv:<investment_id>`) and queues `l2_pool_failed` per investor with the **reason** ("didn't reach its target by the deadline"), the **refund amount** (Σ `funded_received_minor` of that investor's refunding investments) and the expected timing. A cancellation-pending or unapplied fund move that arrives later gets its own notice when it does (below).
- **Investor cancellation (227.304(a)):** `cancel_investment` queues `l2_investment_cancelled` in its transaction — `reserved` with no provider call: "cancelled, nothing was charged"; `reserved` with a provider call started (round 4, finding 2): `l2_cancel_pending` ("if any payment was taken it will be refunded in full"), then from the §4.3 resolution either `l2_investment_cancelled` "nothing was charged" (no trade / trade voided) or, when the fund move settles, `l2_investment_cancelled` with the received amount; `funded`: cancelled, reason "cancelled at your request", refund amount = `funded_received_minor`; `funding`: `l2_cancel_pending` ("Cancellation received — we'll refund your payment in full as soon as it arrives"), then `l2_investment_cancelled` with the received amount when `record_investment_funded` moves it to `refund_pending`.
- **Unapplied fund move (§3.1):** `record_investment_funded`'s unapplied path queues `l2_payment_refunded_unapplied` with the reason (`reservation_expired`, `offering_closed`, `amount_mismatch`, …) and the received amount.
- **Timing:** every refund op is created in the same transaction as the event that makes the refund owed, so funds are directed at once; policy `l2.refundDirectBusinessDays = 5` bounds it. L2 recon opens **`refund_overdue`** (non-pausing, derived, alert log `refund.overdue`) for a refund op not yet `sent` more than that many business days after it was created (e.g. stuck `failed`/`dead`), so staff see a regulatory-window breach before it happens. `l2_refund_completed` is sent on confirmation as today.
- **Commitment notice and transaction confirmation (17 CFR 227.303(d), (f); PR #10 review round 4, finding 6; FR-L2-INV-004):** `l2_commitment_received` is queued **once per investment** (round 5, finding 2) by whichever runs first: `mark_investment_funding` on its `funding` path, or `record_investment_funded` applied to an investment still `reserved` (its fund-move webhook beat `mark_investment_funding`). The insert carries the dedupe key `commitment_received:<investment_id>` and does nothing on conflict, so the second path never queues another. It carries the commitment amount, Unit price and number of Units, the issuer name (pending L2-Q2) and the cancel-by date and time (`ends_at` − `cancel_cutoff_hours`, with time zone); `/invest/:id/confirmation` shows the same four fields. `settle_pool`'s funded branch queues `l2_units_issued` per issued investment with the transaction date, security type ("revenue-share Units", pending L2-Q2), the investor's Units and price, the Units sold by the issuer in the offering and their price, return cap and maturity date in place of interest rate / yield to maturity (pending L2-Q9), "not callable", and remuneration (platform royalty share "pending fee schedule", L2-Q7; intermediary compensation "pending — L2-Q3"). In production both are the intermediary's (L2-Q9).
- **Demo line (D-2; PR #10 review round 5, finding 6):** every Layer 2 notice template (through the shared footer `L2_DEMO_FOOTER`) and the mock Form C (its first-line notice and the `/pools/:id/form-c` view) contain the D-2 sentence verbatim — "Demo — not an offer of securities. Mock escrow and data." `lint:copy` renders every template in `L2_TEMPLATES` and the Form C and fails if one lacks it.
- Notices are copy-linted (`lint:copy`, D-4) and carry no amounts other than the investor's own (and, in the confirmation, the offering's Units sold and price, which 227.303(f)(1)(iii) requires).

## 6. Revenue ingestion and default (01b §3, §5)
- **Statement** (creator upload, labelled `SELF_REPORTED` whatever the mechanism — PR #10 review round 2, finding 9; `API_VERIFIED` stays in the check constraint for a future distributor-API feed the demo doesn't build, and no demo path writes it, seed included): refused with `pool_matured` when `period_end > matures_at`; period label, period dates, lines by revenue type; `covered_minor` = Σ lines of the Pool's revenue types; SHA-256 over canonical JSON; unique per (Pool, period).
- **Settlement line** (`BANK_RECONCILED`): created only from the provider's `deposit.settled` webhook into the Pool's collection account; reference = period label.
- **Expected periods and statements (PR #10 final review):** `l2_period_windows(pool)` lists the expected windows (below); a statement must name exactly one window (`period_start`/`period_end` equal to the window's first and last UTC day), else `period_not_expected`, and none after maturity (`pool_matured`); only a `funded`/`matured` Pool takes statements (`pool_not_funded`). Enforced by a trigger on `revenue_statements`, so the API (#12) can't write a statement the default rules wouldn't recognise.
- **Reconciliation** (`reconcile_pool_revenue(pool, now)`, idempotent): for each statement not yet fully collected (`reported` or `short` — **short statements are re-reconciled every run**), matched cash = Σ settlement lines with the same reference; collected = min(cash, covered); **each run collects only the increment** over what was already collected, posted with ledger key `revenue.collected:<statement>:<cumulative collected>` so a top-up posts once and a re-run posts nothing; shortfall → `pool_breaks(revenue_shortfall)` (amount updated each run, **resolved `collected` once the statement is fully collected**); overage stays in suspense with a `revenue_overage` break; no cash → "reported, not collected". A statement is `collected` only when cash > 0 covers it — **a zero-cash statement never counts as collected** for default purposes, so uploading a zero statement can't hold off `AT_RISK`.
- **Default:** expected periods are consecutive `l2.periodMonths` windows from close, **stopping at maturity** — the last window ends at `matures_at` and no window starts after it (finding 8); `l2_past_due` counts only those, so a `matured` Pool can still be past due for a missed final period, and its collection state keeps working until cured or charged off. A period is past due when its window ended more than `l2.settlementDueDays` before `now` and no `collected` statement with collected cash > 0 names that window → `AT_RISK`; at risk longer than `l2.cureDays` → `DEFAULT`; `AT_RISK` cured (no period past due any more) → `COLLECTING` automatically. Staff move `DEFAULT → REMEDIATION | CHARGED_OFF`, `REMEDIATION → CHARGED_OFF`, and **`REMEDIATION → COLLECTING`** (PR #10 review, finding 4): staff action `pool.collection_state` through `privileged()` (typed reason, audit), which `set_collection_state` allows only when `l2_past_due(pool, now)` is false — bank-reconciled cash covers every missed period — else `not_cured`. `reconcile_pool_revenue` never moves a Pool out of `REMEDIATION` or `DEFAULT`. Each transition writes an outbox notice to every holder. **Flag off (PR #10 review round 5, finding 4; §2):** while `l2_enabled()` is false `reconcile_pool_revenue` skips the adverse transitions (`COLLECTING → AT_RISK`, `AT_RISK → DEFAULT`) — it still reconciles cash and still cures `AT_RISK → COLLECTING` — and `set_collection_state` (staff `pool.collection_state`) doesn't check the flag, so staff can always move a Pool already in `DEFAULT` or `REMEDIATION`.

## 7. Waterfall (01a §4)
- **Pure function** `allocateWaterfall()` in `packages/shared/src/waterfall.ts` (tested in shared and API). Input: run total C (= the Pool's entire `pool_revenue_unallocated` balance), split bps, holdings `[investmentId, units, capRemainingMinor]` (`capRemainingMinor = cap_minor − distributed_minor`, where `distributed_minor` already includes every committed run whether or not its payouts have confirmed; §7 Commit). Fans pool F = ⌊C·fans/10000⌋; platform P = ⌊C·platform/10000⌋; creator gets the rest. F is split pro-rata by Units with **largest remainder** (ties: investment id ascending); any allocation above an investment's remaining cap is clipped and the excess re-split among uncapped holders; when every holder is capped, the remaining excess goes to the creator (`capOverflowMinor`). Σ(payouts) + creator + platform + overflow == C exactly.
- **Hash:** SHA-256 of canonical JSON of {inputs, outputs} (API side). Dry-run and commit compute the same allocation from the same DB state, so the same hash (AC-W1).
- **Maturity (PR #10 review round 2, finding 8):** the worker moves `funded → matured` (`matured_reason = 'maturity'`) once `now ≥ matures_at`, in its own step under the pool lock, whether or not a run is committed. `commit_distribution_run` accepts a Pool in `funded` **or `matured`**, so cash for periods ending on or before maturity that reconciles later is still distributed (final runs; same caps; investors at cap get nothing more and the excess goes to the creator as cap overflow). A commit never moves a Pool to `matured` by date any more; it does so only when every issued investment ends the run at its cap (`'cap_reached'`).
- **Commit** — what is checked where (PR #10 review, finding 6). **API:** `commitDistribution` recomputes the allocation and its hash from current DB state with `allocateWaterfall()` and refuses `run_stale` unless the hash equals the dry-run's. **SQL** (`commit_distribution_run(pool, label, hash, allocation, now)`) checks, under the pool lock: run total == current `pool_revenue_unallocated` balance (collected-only, AC-W3); conservation fans + creator + platform == run total, creator and platform ≥ 0 (AC-W4); platform == ⌊C·platform bps/10000⌋ and fans ≤ ⌊C·fans bps/10000⌋, with **fans == ⌊C·fans bps/10000⌋ unless every issued investment ends the run at its cap** (only then can there be cap overflow to the creator; PR #10 review round 2, finding 4); every payout is > 0, names an `issued` investment of this Pool, and keeps it within its cap (AC-W2). **SQL does not recompute the pro-rata largest-remainder split**: that the fan amount is divided by Units with largest remainder is enforced by the single shared pure function (used for dry-run and commit) and its tests (W1/W2/W4 properties in `packages/shared`, plus an API test that a committed run equals `allocateWaterfall()` of the same inputs). It then posts the allocation, **adds each payout to its investment's `distributed_minor` in the same transaction** — cap usage counts at commit, not at payout confirmation (round 3, finding 11), so the next run's caps, the `cap_reached` check and the "at its cap" test above all see committed-but-unpaid amounts, and a payout still `sent` can't be allocated twice — creates payouts and their ops (`payout:<distribution_payout_id>`, §5); unique (Pool, label) → a second commit with the same hash returns the first run, a different hash is refused (AC-W6). If every issued investment reaches its cap, the Pool becomes `matured` (`cap_reached`); maturity by date is the worker's step above.
- **Tax:** each investor payout records `tax_characterization = 'dividend'` (form `1099-DIV`, Mechanism 04 default, **counsel item L2-Q6**) and upserts `tax_1099_rows(year, investor, pool)`.
