## 2. Flag enforcement (FR-PLT-001 slice for `layer2`)
- **Database:** `platform_settings['flag.layer2']` (default `false`, audited changes through staff action `flag.set`). `public.l2_enabled()` reads it; every Layer 2 money/workflow function starts with `perform public.l2_assert_enabled()` → raises `layer2_disabled`.
- **API:** Layer 2 route plugins register a `preHandler` that returns 404 `layer2_disabled` unless `REGCF_PROVIDER=mock` **and** the DB flag is on. `REGCF_PROVIDER=mock` is refused at startup in a deployed environment (same rule as the M1 sandbox), so Layer 2 can't be on in production by construction.
- **Web:** `/v1/config` reports `flags.layer2` from the server. Layer 2 pages that read data render the "isn't open yet" state when the API says `layer2_disabled`; the client `?flags=` override only reveals mock-only screens (unchanged), never data. Every `layer2` route renders `Layer2DemoBanner` (inside `FeatureRoute`).

| Event | Posting |
|---|---|
| Fund move settled | +escrow / −investor_liability |
| Refund settled | +investor_liability / −escrow |
| Pool closes (funded) | +investor_liability / −issuer_payable (total raised) |

Invariants (tests): AC-E1 pre-close `escrow == Σ amount of funded + refund_pending investments` after every committed money function, and `escrow == provider escrow` compared after the inbox is drained or with in-flight amounts reported separately (§5.1; PR #10 review, finding 5); post-close `escrow == raised at close − Σ released tranches + Σ refund_pending not yet refunded`; AC-E5 escrow ≥ 0 and 0 at the end; `collection == provider collection balance`; unallocated only grows from reconciliation (AC-W3/R1).

**Investments** state machine: `reserved → funding → funded → issued`; `reserved → expired | cancelled`; `funding → returned`; `funded → refund_pending → refunded`. Limit usage counts `reserved` (unexpired), `funding`, `funded`, `issued`, `refund_pending`.
**Cancellation (PR #10 review, finding 9):** `cancel_investment` before the 48-hour cut-off: `reserved → cancelled` (Units back); `funded → refund_pending` (refund op for the full amount); **`funding` is refused** with `409 funding_in_progress` — we never refund money that hasn't arrived, and we don't queue a cancellation behind an in-flight fund move. The investor retries once the webhook has made it `funded`; the cut-off isn't extended.
**Counter rule (M1 §3.5, as on `main`):** `pools.raised_minor` and `investors_count` count only `funded` (and, after close, `issued`) investments; `units_committed` also counts unexpired `reserved` and `funding`. Every function that moves an investment out of a counted state (`cancel_investment`, the failed branch of `settle_pool`, `record_investment_returned`, reservation expiry) adjusts the counters **in the same transaction**, never at refund confirmation. `settle_pool`'s funded branch issues **only `funded`** investments; `refund_pending` ones finish refunding from escrow through their op and are never part of the amount closed to the issuer.
**Issuer cap (PR #10 review, finding 1):** `pools.duration_days` check `21–60` (`regCf.minOfferingDays`, finding 2); `pools.issuer_cap_remaining_minor` is written by `launch_pool` (§4.1).

**Pool** status: `draft → in_review → (revisions_requested → in_review) → approved → live → funded | failed → refunded`; `funded → matured` (cap reached or maturity) ; `draft|… → withdrawn`. Collection state separate: `COLLECTING, AT_RISK, DEFAULT, REMEDIATION, CHARGED_OFF`.

## 4. Concurrency: the investment limit (01a §3, AC-I1/I2/I5)
`reserve_investment` runs in one transaction: lock `investor_profiles` row (`for update`) → lock `pools` row → check KYC, state, flag, deadline, self-investment, min Units, availability (`units_committed + n ≤ units_total`), **issuer cap** (`committed amount + n × price ≤ issuer_cap_remaining_minor`, else `issuer_cap_reached`, §4.1) → usage = Σ amount of the investor's counted investments created in the trailing 12 months + self-reported elsewhere → refuse `regcf_limit_exceeded` if usage + amount > limit → insert `reserved` with `reserve_expires_at = now() + l2.reserveMinutes`. The investor lock serialises one person's purchases across all offerings, so N concurrent purchases admit exactly those that fit. Expiry (worker) and returned fund moves free the headroom (AC-I2). The limit formula and thresholds live in `packages/shared/src/policy.ts` (`regCf`) and are mirrored in `platform_settings['regcf_limits']` (sync test).

### 4.1 Issuer cap (PR #10 review, finding 1)
Remaining 12-month cap for a creator = tier cap (`tier_limits.reg_cf_cap_minor`, never above `POLICY.regCf.issuerCapMinor`) − Σ over the creator's **other** Pools of `raised_minor` for those closed (`funded`/`matured`) in the trailing 12 months and `max_minor` for those `in_review`/`approved`/`live`. `submit_pool` and `launch_pool` both lock the artist row (`for update`) and refuse `tier_cap_exceeded` when this Pool's **`max_minor`** (Units × price) exceeds the remaining cap; `launch_pool` writes the remaining cap it checked to `pools.issuer_cap_remaining_minor`. `reserve_investment` refuses a reservation that would take Σ amount of the Pool's `reserved` + `funding` + `funded` investments past it. With the launch check this can only bite if the cap changed after launch; it is the backstop that keeps sales under the cap whatever the target/maximum gap.

### 4.2 Lock order (aligned with M1 §3.5.1 on `main`)
Every Layer 2 money function locks in the order **investor profile → artist → pool → investment(s) → pool tranche / distribution payout**, and takes only the suffix it needs. Functions that start from an investment, tranche or payout id read its `pool_id` unlocked (it never changes), lock the pool, then the row — the order `settle_pool` and `commit_distribution_run` use — so a fund-move webhook, a cancellation or a refund confirmation racing the deadline can't deadlock with settlement. **Lock, then check:** functions keyed by a ledger idempotency key (`record_investment_funded`, `record_investment_refunded`, `record_pool_tranche_released`, `record_pool_payout_confirmed`) take their locks **before** checking for the key, so two processors racing on one event serialise: one posts, the other returns `'duplicate'`. Reservation expiry locks per Pool (pool, then its expired reservations), not investment-first.

## 5. Provider boundary and flows (ADR-007)
`RegCfProvider` (TransactAPI-shaped): `createIssuer`, `createOffering`, `updateOfferingStatus`, `createParty`, `setPartyKyc`, `createAccount`, `createLink`, `createTrade`, `fundTrade` (fund move into escrow), `getTrade`, `getEscrow`, `closeOffering`, `disburseToIssuer`, `refundTrade`, `createCollectionAccount`, `getCollectionAccount`, `payoutFromCollection`, `simulateDeposit` (mock-only test trigger), `parseWebhook` (HMAC verify). Every mutating call carries an idempotency key derived from our row id, so a retry returns the original object (the two-phase op only needs "call again with the same key").

- **Launch:** API calls `createIssuer`/`createOffering`/`createCollectionAccount` (keys `issuer:<artist>`, `offering:<pool>`, `collection:<pool>`), then `launch_pool(refs)`, which re-checks the issuer cap on the maximum under the artist lock (§4.1) and requires `duration_days ≥ regCf.minOfferingDays`. Retry-safe. The provider offering's end date is derived from the stored Pool row (deterministic params, as M1 §4.4 step 3), so a retried launch replays the same objects.
- **Purchase:** `reserve_investment` → `createTrade` (key `trade:<investment>`) → `fundTrade` (key `fund:<investment>`) → `mark_investment_funding`. Fund move settles asynchronously → webhook `fund_move.settled` → `record_investment_funded`. Returned → `record_investment_returned`. **Idempotency-Key exactly as M1 §4.4 on `main`:** the `api_idempotency` claim (`investments:<user>:<key>`) and `reserve_investment` run in **one transaction** (reservation under a savepoint); a rule violation (`regcf_limit_exceeded`, `pool_sold_out`, `issuer_cap_reached`, `kyc_required`, …) rolls back to the savepoint and is **stored on the claim as `done` with its 4xx response**, so a retry replays it; the 2-minute abandoned-claim rule is the backstop; before every provider call (first pass and resume) a **resume guard** re-reads the investment and returns the terminal, stored `409 reservation_expired` unless it is `reserved` with `reserve_expires_at > now()` and the Pool is `live` before `ends_at`; every `createTrade`/`fundTrade` parameter is derived from the stored investment row, never the request.
- **Settlement:** worker `settle_pool(now)` after the deadline (waits up to `l2.settleGraceMinutes` for in-flight fund moves). Funded → ledger close of Σ `funded` amounts, only `funded` investments issued (lock-up end = close + 12 months), tranche 1 verified, outbox `l2.op` close + disburse. Failed → `refund_pending` + refund op for every funded investment, counters adjusted in the same transaction (counter rule, §3). The deadline is never less than 21 days after launch (`regCf.minOfferingDays`), so the earliest transmission to the issuer is at least 21 days after the offering information was posted (17 CFR 227.303(e)(3)(i)).
- **Outbound:** `pool_ops` (kinds `refund`, `disburse`, `payout`, `close_offering`), same states **and rules** as M1 `outbound_ops` on `main` (M1 §3.3, §5): the runner claims a due op with a lease **and a fresh `claim_token`**, and every outcome write (`sent`, `confirmed`, `failed`, `dead`, back to `initiated`) applies only `where claim_token = <ours>`, so a runner that outlived its lease can't overwrite the state of the one that re-claimed the op; `call_started_at` is set once, in the transaction just before the first provider call. `close_offering` confirms on the response; the others are `sent` until the webhook confirms; the SQL confirm function asserts the exact amount.
  - **Never a stale amount; tranches in order:** a refund op's amount is fixed when the op is created (the funded amount, or what actually arrived for an unapplied fund move). A `disburse` op's amount is `pool_tranche_release_amount()`, which depends on earlier releases (the last tranche is owed whatever `pool_issuer_payable` still holds), so: (1) a tranche's disburse op is created only when **every earlier tranche is `released`** — `verify_pool_tranche` queues it only then, and `record_pool_tranche_released` locks the next tranche and queues its op if it is already `verified`; (2) right before the first provider call the runner re-derives the amount and, in the transaction that sets `call_started_at`, updates the op if no call has started; (3) once `call_started_at` is set the amount is frozen — if what is owed later differs, the op fails `permanent` (`disburse_amount_changed`, alert) instead of sending the old figure. Distribution `payout` ops are fixed at commit (the run is immutable).
- **Webhooks:** `POST /api/v1/webhooks/regcf`, header `x-mock-escrow-signature: t=<unix>,v1=<hex hmac-sha256(secret, t + "." + rawBody)>`, 5-minute tolerance. Stored in `provider_events` (`provider='mock-escrow'`, unique event id) before processing; duplicate deliveries are no-ops; processing failures retry with the M1 inbox backoff. **Processing goes through the M1 inbox processor on `main` only** (M1 §3.2): every processor (inline attempt, worker, staff replay) claims the row (`processing`, `lease_until = now() + 5 min`, fresh `claim_token`) before work, and every outcome write — including the "wait for the matching row" path back to `received` — is conditional on `status = 'processing' and claim_token = <ours>`; Layer 2 adds a `regcf.*` branch to the dispatcher, never its own claim or status writes.

### 5.1 Layer 2 reconciliation and pause rule (aligned with M1 §7 on `main`)
- **Per Pool:** ledger `pool_escrow` vs provider escrow and ledger `pool_collection` vs provider collection balance. **In-flight allowance (M1 pattern):** amounts belonging to a `pool_ops` row still `sent`, or to a `regcf.*` event received less than `recon.inflightGraceMinutes` ago and not yet processed, are reported in the run's `inFlight` list and left out of the difference, so they open no break (AC-E1, finding 5). Past the grace they count.
- **Breaks** live in `pool_breaks` (never `recon_breaks`), so Layer 2 activity can't move M1's per-campaign diff or its `PAYOUT_PAUSING_KINDS` (gate condition 1). **Layer 2 pausing kinds** (`L2_PAYOUT_PAUSING_KINDS`, next to M1's in `apps/api/src/recon.ts`): `escrow_diff`, `collection_diff`, `unapplied_funding`. An open one on a Pool with `|amount| > recon.materialityMinor` or older than `recon.maxBreakAgeBusinessDays` pauses **that Pool's** `disburse` and `payout` ops (left `initiated`, retried later); refunds never pause. `revenue_shortfall` and `revenue_overage` never pause: shortfall cash was never collected and overage stays in suspense, so neither can be distributed. Derived breaks auto-resolve `cleared_by_run`; `unapplied_funding` stays open until staff resolve it, as M1's `amount_mismatch`.

## 6. Revenue ingestion and default (01b §3, §5)
- **Statement** (`API_VERIFIED` mock distributor statement): period label, period dates, lines by revenue type; `covered_minor` = Σ lines of the Pool's revenue types; SHA-256 over canonical JSON; unique per (Pool, period).
- **Settlement line** (`BANK_RECONCILED`): created only from the provider's `deposit.settled` webhook into the Pool's collection account; reference = period label.
- **Reconciliation** (`reconcile_pool_revenue(pool, now)`, idempotent): for each unreconciled statement, matched cash = Σ settlement lines with the same reference; collected = min(cash, covered); shortfall → `pool_breaks(revenue_shortfall)`; overage stays in suspense with a `revenue_overage` break; no cash → "reported, not collected". Posts `revenue.collected:<statement>` once.
- **Default:** expected periods are consecutive `l2.periodMonths` windows from close. A period is past due when `period_end + l2.settlementDueDays < now` and it isn't fully collected → `AT_RISK`; at risk longer than `l2.cureDays` → `DEFAULT`; `AT_RISK` cured (no period past due any more) → `COLLECTING` automatically. Staff move `DEFAULT → REMEDIATION | CHARGED_OFF`, `REMEDIATION → CHARGED_OFF`, and **`REMEDIATION → COLLECTING`** (PR #10 review, finding 4): staff action `pool.collection_state` through `privileged()` (typed reason, audit), which `set_collection_state` allows only when `l2_past_due(pool, now)` is false — bank-reconciled cash covers every missed period — else `not_cured`. `reconcile_pool_revenue` never moves a Pool out of `REMEDIATION` or `DEFAULT`. Each transition writes an outbox notice to every holder.

## 7. Waterfall (01a §4)
- **Pure function** `allocateWaterfall()` in `packages/shared/src/waterfall.ts` (tested in shared and API). Input: run total C (= the Pool's entire `pool_revenue_unallocated` balance), split bps, holdings `[investmentId, units, capRemainingMinor]`. Fans pool F = ⌊C·fans/10000⌋; platform P = ⌊C·platform/10000⌋; creator gets the rest. F is split pro-rata by Units with **largest remainder** (ties: investment id ascending); any allocation above an investment's remaining cap is clipped and the excess re-split among uncapped holders; when every holder is capped, the remaining excess goes to the creator (`capOverflowMinor`). Σ(payouts) + creator + platform + overflow == C exactly.
- **Hash:** SHA-256 of canonical JSON of {inputs, outputs} (API side). Dry-run and commit compute the same allocation from the same DB state, so the same hash (AC-W1).
- **Commit** — what is checked where (PR #10 review, finding 6). **API:** `commitDistribution` recomputes the allocation and its hash from current DB state with `allocateWaterfall()` and refuses `run_stale` unless the hash equals the dry-run's. **SQL** (`commit_distribution_run(pool, label, hash, allocation, now)`) checks, under the pool lock: run total == current `pool_revenue_unallocated` balance (collected-only, AC-W3); conservation fans + creator + platform == run total, creator and platform ≥ 0 (AC-W4); platform == ⌊C·platform bps/10000⌋ and fans ≤ ⌊C·fans bps/10000⌋ (the gap is cap overflow to the creator); every payout is > 0, names an `issued` investment of this Pool, and keeps it within its cap (AC-W2). **SQL does not recompute the pro-rata largest-remainder split**: that the fan amount is divided by Units with largest remainder is enforced by the single shared pure function (used for dry-run and commit) and its tests (W1/W2/W4 properties in `packages/shared`, plus an API test that a committed run equals `allocateWaterfall()` of the same inputs). It then posts the allocation, creates payouts and outbox ops; unique (Pool, label) → a second commit with the same hash returns the first run, a different hash is refused (AC-W6). If every investment reaches its cap, or the run's `now` is past maturity, the Pool becomes `matured`.
- **Tax:** each investor payout records `tax_characterization = 'dividend'` (form `1099-DIV`, Mechanism 04 default, **counsel item L2-Q6**) and upserts `tax_1099_rows(year, investor, pool)`.

## 8. Collection mechanism → risk badge (Mechanism 01, 01b §1.1)
Strength: `DISTRIBUTOR_REDIRECT`=3, `SPLIT_PAYEE`=3, `LOCKBOX`=2, `LETTER_OF_DIRECTION`=2, `SELF_REPORT`=1. Revenue-type ceiling: master=3, sync=2, publishing=1 ("Trust-based — pending counsel"). Effective = min over the Pool's revenue types of min(mechanism, ceiling). Badge: 3 → `SECURED_ISH`, 2 → `VERIFIED`, 1 → `TRUST_BASED` (internal names, never in copy). **Labels (one wording everywhere; PR #10 review, finding 3):** "More secure collection", "Verified collection", "Trust-based collection" (`RISK_BADGE_COPY` in `l2.ts`). Wherever a fan sees the strongest badge — Pool cards, Pool page, documents/purchase, portfolio, holding — the separate line **"Your claim is unsecured"** is rendered next to it (gate condition 5). Computed in `packages/shared/src/l2.ts` and by SQL at submission (sync test).

## 12. Security & compliance notes
- No PII stored by FanZuP for Layer 2 beyond state and the investor's own attested income/net-worth figures (needed for the limit; service-role only, never returned to other users). Legal names go to the provider only.
- Clients have no grants on Layer 2 money/PII tables; reads go through the API (owner- or staff-scoped).
- Reviewer ≠ owner for Form C review, tranche verification, collection execution; staff can't decide their own KYC.
- The mock provider and dev routes can't run deployed; webhook secret and API key come from env (dev defaults only when not deployed).
