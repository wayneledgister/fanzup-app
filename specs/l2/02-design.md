## 2. Flag enforcement (FR-PLT-001 slice for `layer2`)
- **Database:** `platform_settings['flag.layer2']` (default `false`, audited changes through staff action `flag.set`). `public.l2_enabled()` reads it; every Layer 2 money/workflow function starts with `perform public.l2_assert_enabled()` → raises `layer2_disabled`.
- **API:** Layer 2 route plugins register a `preHandler` that returns 404 `layer2_disabled` unless `REGCF_PROVIDER=mock` **and** the DB flag is on. `REGCF_PROVIDER=mock` is refused at startup in a deployed environment (same rule as the M1 sandbox), so Layer 2 can't be on in production by construction. **One route is outside the gate (PR #10 review round 2, finding 5):** the flag switch itself, `POST /api/v1/staff/flags/layer2` in the M1 staff plugin (`apps/api/src/routes/staff.ts`) — it can't sit behind the gate it opens. It is gated only by staff role + **aal2** + `privileged()` (action `flag.set`: typed reason, audit, single-operator rules), and turning the flag on is refused with `409 provider_missing` unless the API runs with `REGCF_PROVIDER=mock` — which it never does deployed.
- **Web:** `/v1/config` reports `flags.layer2` from the server. Layer 2 pages that read data render the "isn't open yet" state when the API says `layer2_disabled`; the client `?flags=` override only reveals mock-only screens, never data. **Production builds (PR #10 review round 2, finding 6):** in a production web build (`import.meta.env.PROD`) `useFlag('layer2')` is the server's `flags.layer2` only — the `?flags=layer2` override, its sessionStorage copy and `VITE_FLAG_LAYER2` are ignored for `layer2` — so a shared `?flags=layer2` link can't show Layer 2 screens from a deployed site (E1 readiness condition 1). The override keeps working in the Vite dev server (`pnpm dev`) for reviewing mock-only screens; screenshots of gated pages use the dev server or a local API with the server flag on. Every `layer2` route renders `Layer2DemoBanner` (inside `FeatureRoute`).

Invariants (tests): AC-E1 pre-close `escrow == Σ funded_received_minor of funded + refund_pending investments + Σ open stray fund moves` (§3.1; the **received** amount, PR #10 review round 2, finding 3) after every committed money function, and `escrow == provider escrow` compared after the inbox is drained or with in-flight amounts reported separately (§5.1; PR #10 review, finding 5); post-close `escrow == raised at close − Σ released tranches + Σ funded_received_minor of refund_pending not yet refunded + Σ open stray fund moves`; **liability** (credit balance of `pool_investor_liability`) `== Σ funded_received_minor of funded + refund_pending investments + Σ open stray fund moves` before and after close (issued investments' liability has moved to `pool_issuer_payable`); AC-E5 escrow ≥ 0 and 0 at the end; `collection == provider collection balance`; unallocated only grows from reconciliation (AC-W3/R1).

**Investments** state machine: `reserved → funding → funded → issued`; `reserved → expired | cancelled`; `funding → returned`; `funded → refund_pending → refunded`; `funding → refund_pending` (fund move settles on a cancellation-pending investment, below); `reserved | funding | expired | cancelled → refund_pending` (a first fund move that can't be applied, §3.1). New columns: `funded_received_minor` (what the fund move delivered, set by `record_investment_funded` on both the applied and the unapplied path; the refund op and `record_investment_refunded` use it), `cancel_requested_at`, `provider_call_started_at` (§5 purchase). Limit usage counts `reserved` (unexpired), `funding`, `funded`, `issued`, `refund_pending` (same list as FR-L2-INV-003; finding 10).
**Cancellation (PR #10 review round 2, finding 1; replaces the round-1 refusal in `funding`):** `cancel_investment(inv, user, now)` judges the 48-hour cut-off at **request time** and, before it: `reserved → cancelled` (Units back); `funded → refund_pending` (refund op for `funded_received_minor`); **`funding`: accepted and recorded** — sets `cancel_requested_at = now` (status stays `funding`), returns `'cancel_pending'` (API 200 `{ result: 'cancel_pending' }`; the fan sees "Cancellation received — we'll refund your payment in full as soon as it arrives"); a repeat request returns `'cancel_pending'` again. Then: `record_investment_funded` on an investment with `cancel_requested_at` set **never makes it `funded`** — it posts the fund move as received, sets `funded_received_minor`, moves it straight to `refund_pending` (`status_reason = 'cancelled_by_investor'`) and queues the full refund op, whenever the fund move settles (after the cut-off, after the deadline, after settlement); `record_investment_returned` simply closes it as `returned` (no money arrived). `settle_pool` never issues a cancellation-pending investment (it issues only `funded`). We never refund money that hasn't arrived; the investor's right to cancel is fixed when they ask.
**Counter rule (M1 §3.5, as on `main`):** `pools.raised_minor` and `investors_count` count only `funded` (and, after close, `issued`) investments; `units_committed` also counts unexpired `reserved` and `funding`. Every function that moves an investment out of a counted state (`cancel_investment`, the failed branch of `settle_pool`, `record_investment_returned`, reservation expiry, and `record_investment_funded` on its cancellation-pending and unapplied paths — `funding`/`reserved` → `refund_pending` releases `units_committed` and never adds to `raised_minor`/`investors_count`) adjusts the counters **in the same transaction**, never at refund confirmation. A stray fund move (§3.1) changes no counter. `settle_pool`'s funded branch issues **only `funded`** investments; `refund_pending` ones finish refunding from escrow through their op and are never part of the amount closed to the issuer.
**Issuer cap (PR #10 review, finding 1):** `pools.duration_days` check `21–60` (`regCf.minOfferingDays`, finding 2); `pools.issuer_cap_remaining_minor` is written by `launch_pool` (§4.1).

**Pool** status: `draft → in_review → (revisions_requested → in_review) → approved → live → funded | failed → refunded`; `funded → matured` — by the worker at `matures_at` (`matured_reason = 'maturity'`, time-based, whether or not a run is committed) or by a commit after which every issued investment is at its cap (`'cap_reached'`); a `matured` Pool still accepts reconciliation and final distribution runs (§6, §7; PR #10 review round 2, finding 8); `draft|… → withdrawn`. Collection state separate: `COLLECTING, AT_RISK, DEFAULT, REMEDIATION, CHARGED_OFF`.

### 3.1 Matching a fund move; fund moves we can't apply (PR #10 review round 2, finding 3; follows M1 §3.5.1)
A fund move is money in the offering escrow; once the provider says it settled, it is posted — every time, exactly once — and either applied to one investment or refunded in full from what actually arrived. As M1 §3.5.1 does for captures:
1. **Match by fund ref first:** the investment whose `provider_fund_ref` equals the event's fund move id.
2. **Else by the fund move's `externalId`** (our investment id), only if that investment's `provider_fund_ref` is null (the webhook beat `mark_investment_funding`) or equal.
3. **Same fund move again** → idempotency key `fund:<fund_ref>` already posted → `'duplicate'`, nothing moves (lock-then-check, §4.2).
4. **Stray fund move** — one that names an investment whose `provider_fund_ref` is a *different* ref, or an investment that already had a fund move applied (`funded`, `issued`, `refund_pending`, `refunded`, `returned`), or that names no investment but carries our offering: `record_stray_fund_move(pool, fund_ref, amount)` posts `investment.funded_stray` (+`pool_escrow` / −`pool_investor_liability`, `external_ref = fund_ref`, idempotency key `fund:<fund_ref>`), changes **no investment state and no counter**, and creates **its own refund op keyed by the fund ref**: `pool_ops(kind 'refund', subject_id = the provider_events row id, fund_ref, amount_minor = received amount, idempotency_key = refund:fund:<fund_ref>)`. Its confirmation, `record_stray_fund_refund_confirmed(fund_ref, refund_ref, amount, idem)`, checks the amount against the stray and posts `investment.stray_refunded` (reverse legs). Alert log `fund_move.stray`; the op shows in the staff Pool money view. An open stray (refund not confirmed) counts in expected escrow and liability (§3, §5.1); one whose refund op is unconfirmed past `recon.maxBreakAgeBusinessDays` opens a `stray_fund_move_aged` break.
5. A fund move matching no investment and no offering stays `unmatched` in the inbox for staff (M1 §5).

**`record_investment_funded(inv, fund_ref, amount, idem, now)`** (steps 1–3 matched it to `inv`): locks pool → investment, then checks `idem`; re-checks under the lock that the investment's `provider_fund_ref` is null or `fund_ref` and that no fund move was applied to it yet — otherwise returns `'stray'` and the caller hands the event to `record_stray_fund_move`. It always stores `funded_received_minor = amount` and `provider_fund_ref`, posts the fund move once (+escrow / −liability), then:
- **Applied** (`'applied'`) only when all hold: status `reserved` with `reserve_expires_at > now` or `funding`; no `cancel_requested_at`; Pool `live` (not yet settled — `settle_pool` runs at `ends_at` and waits up to `l2.settleGraceMinutes` for `funding` investments, so a fund move after settlement is late); `amount = amount_minor`. → `funded`, `raised_minor += amount`, investors recounted (counter rule).
- **Cancellation pending** (`'refund:cancelled_by_investor'`): `cancel_requested_at` set → `refund_pending`, refund op for `amount` (§3 Cancellation).
- **Unapplied** (`'refund:<reason>'`, reasons `amount_mismatch`, `reservation_expired`, `reservation_cancelled`, `offering_closed`): status `reserved`/`funding`/`expired`/`cancelled` → `refund_pending` with the reason, refund op for the **received** `amount`; Units leave `units_committed` if they were still counted (`reserved`/`funding`), `raised_minor` never changes (counter rule). `amount_mismatch` also opens an `unapplied_funding` break (staff-resolved, pausing).
The refund op of an investment is `pool_ops(kind 'refund', subject_id = investment id, idempotency_key = refund:<investment>)`; `record_investment_refunded` requires `amount = funded_received_minor`. Uniqueness of `pool_ops` is the **idempotency key alone** (no `unique(kind, subject_id)`), so an investment refund and a stray refund on the same Pool never collide, and a second refund for one investment can only arise from a second key — which this section never creates.

## 4. Concurrency: the investment limit (01a §3, AC-I1/I2/I5)
`reserve_investment` runs in one transaction: lock `investor_profiles` row (`for update`) → lock `pools` row → check KYC, state, flag, deadline, self-investment, min Units, availability (`units_committed + n ≤ units_total`), **issuer cap** (`committed amount + n × price ≤ issuer_cap_remaining_minor`, else `issuer_cap_reached`, §4.1) → usage = Σ amount of the investor's counted investments created in the trailing 12 months + self-reported elsewhere → refuse `regcf_limit_exceeded` if usage + amount > limit → insert `reserved` with `reserve_expires_at = now() + l2.reserveMinutes`. The investor lock serialises one person's purchases across all offerings, so N concurrent purchases admit exactly those that fit. Expiry (worker) and returned fund moves free the headroom (AC-I2). The limit formula and thresholds live in `packages/shared/src/policy.ts` (`regCf`) and are mirrored in `platform_settings['regcf_limits']` (sync test).

### 4.1 Issuer cap (PR #10 review, finding 1)
Remaining 12-month cap for a creator = tier cap (`tier_limits.reg_cf_cap_minor`, never above `POLICY.regCf.issuerCapMinor`) − Σ over the creator's **other** Pools of `raised_minor` for those closed (`funded`/`matured`) in the trailing 12 months and `max_minor` for those `in_review`/`approved`/`live`. `submit_pool` and `launch_pool` both lock the artist row (`for update`) and refuse `tier_cap_exceeded` when this Pool's **`max_minor`** (Units × price) exceeds the remaining cap; `launch_pool` writes the remaining cap it checked to `pools.issuer_cap_remaining_minor`. `reserve_investment` refuses a reservation that would take Σ amount of the Pool's `reserved` + `funding` + `funded` investments past it. With the launch check this can only bite if the cap changed after launch; it is the backstop that keeps sales under the cap whatever the target/maximum gap.

### 4.2 Lock order (aligned with M1 §3.5.1 on `main`)
Every Layer 2 money function locks in the order **investor profile → artist → pool → investment(s) → pool tranche / distribution payout**, and takes only the suffix it needs. Functions that start from an investment, tranche or payout id read its `pool_id` unlocked (it never changes), lock the pool, then the row — the order `settle_pool` and `commit_distribution_run` use — so a fund-move webhook, a cancellation or a refund confirmation racing the deadline can't deadlock with settlement. **Lock, then check:** functions keyed by a ledger idempotency key (`record_investment_funded`, `record_investment_refunded`, `record_pool_tranche_released`, `record_pool_payout_confirmed`) take their locks **before** checking for the key, so two processors racing on one event serialise: one posts, the other returns `'duplicate'`. `record_stray_fund_move` and `record_stray_fund_refund_confirmed` serialise on an advisory lock keyed by the fund ref, after the pool lock (M1 §3.5.1). Reservation expiry locks per Pool (pool, then its expired reservations), not investment-first.

## 5. Provider boundary and flows (ADR-007)
`RegCfProvider` (TransactAPI-shaped): `createIssuer`, `createOffering`, `updateOfferingStatus`, `createParty`, `setPartyKyc`, `createAccount`, `createLink`, `createTrade`, `fundTrade` (fund move into escrow), `getTrade`, `getEscrow`, `closeOffering`, `disburseToIssuer`, `refundTrade`, `createCollectionAccount`, `getCollectionAccount`, `payoutFromCollection`, `simulateDeposit` (mock-only test trigger), `parseWebhook` (HMAC verify). Every mutating call carries an idempotency key derived from our row id, so a retry returns the original object (the two-phase op only needs "call again with the same key").

- **Launch:** API calls `createIssuer`/`createOffering`/`createCollectionAccount` (keys `issuer:<artist>`, `offering:<pool>`, `collection:<pool>`), then `launch_pool(refs)`, which re-checks the issuer cap on the maximum under the artist lock (§4.1) and requires `duration_days ≥ regCf.minOfferingDays`. Retry-safe. The provider offering's end date is derived from the stored Pool row (deterministic params, as M1 §4.4 step 3), so a retried launch replays the same objects.
- **Purchase:** `reserve_investment` → `createTrade` (key `trade:<investment>`) → `fundTrade` (key `fund:<investment>`) → `mark_investment_funding`. Fund move settles asynchronously → webhook `fund_move.settled` → `record_investment_funded`. Returned → `record_investment_returned`. **Idempotency-Key exactly as M1 §4.4 on `main`:** the `api_idempotency` claim (`investments:<user>:<key>`) and `reserve_investment` run in **one transaction** (reservation under a savepoint); a rule violation (`regcf_limit_exceeded`, `pool_sold_out`, `issuer_cap_reached`, `kyc_required`, …) rolls back to the savepoint and is **stored on the claim as `done` with its 4xx response**, so a retry replays it; the 2-minute abandoned-claim rule is the backstop; before every provider call (first pass and resume) a **resume guard** re-reads the investment (PR #10 review round 2, finding 2 — in Layer 2 `fundTrade` moves money at the provider, so a crash after the fund move but before the claim is stored `done` must not turn a purchase into "expired"): (a) `funding`, `funded`, `issued`, or `refund_pending`/`refunded` (money moved for this claim) → store and return the **success** response (201 `{ investmentId, status: <current>, amountMinor, units }`), no provider call; (b) `expired` or `cancelled` → terminal stored `409 reservation_expired`; `returned` → terminal stored `409 funding_returned` ("Your bank returned the payment. Start again from the Pool page."); (c) `reserved`, unexpired, Pool `live` before `ends_at` → set `provider_call_started_at` (committed before the first call, M1 `call_started_at` pattern) and call the provider; (d) `reserved` but dead (expired time or Pool not live) **and `provider_call_started_at` null** → terminal stored `409 reservation_expired`, no provider call; (e) `reserved` but dead **with `provider_call_started_at` set** (a crash between the calls and `mark_investment_funding`) → replay `createTrade`/`fundTrade` with the same keys — the provider returns the objects it already created — and `mark_investment_funding` records the refs and returns the status, which the response reports (a fund move for a dead reservation is refunded in full on arrival, §3.1); every `createTrade`/`fundTrade` parameter is derived from the stored investment row, never the request.
- **Settlement:** worker `settle_pool(now)` after the deadline (waits up to `l2.settleGraceMinutes` for in-flight fund moves). Funded → ledger close of Σ `funded` amounts, only `funded` investments issued (lock-up end = close + 12 months), tranche 1 verified, outbox `l2.op` close + disburse. Failed → `refund_pending` + refund op (for `funded_received_minor`) for every funded investment, counters adjusted in the same transaction (counter rule, §3). A `funding` investment still in flight after the grace is not issued and not counted; when its fund move settles, the Pool is no longer `live`, so it is unapplied (`offering_closed`) and refunded in full (§3.1). The deadline is never less than 21 days after launch (`regCf.minOfferingDays`), so the earliest transmission to the issuer is at least 21 days after the offering information was posted (17 CFR 227.303(e)(3)(i)).
- **Outbound:** `pool_ops` (kinds `refund`, `disburse`, `payout`, `close_offering`), same states **and rules** as M1 `outbound_ops` on `main` (M1 §3.3, §5): the runner claims a due op with a lease **and a fresh `claim_token`**, and every outcome write (`sent`, `confirmed`, `failed`, `dead`, back to `initiated`) applies only `where claim_token = <ours>`, so a runner that outlived its lease can't overwrite the state of the one that re-claimed the op; `call_started_at` is set once, in the transaction just before the first provider call. `close_offering` confirms on the response; the others are `sent` until the webhook confirms; the SQL confirm function asserts the exact amount, and a provider amount that differs leaves the event failed (dead-letter) and opens an `amount_mismatch` break (§5.1).
  - **Never a stale amount; tranches in order:** a refund op's amount is fixed when the op is created: always what actually arrived (`funded_received_minor`, or the stray's received amount, §3.1). A `disburse` op's amount is `pool_tranche_release_amount()`, which depends on earlier releases (the last tranche is owed whatever `pool_issuer_payable` still holds), so: (1) a tranche's disburse op is created only when **every earlier tranche is `released`** — `verify_pool_tranche` queues it only then, and `record_pool_tranche_released` locks the next tranche and queues its op if it is already `verified`; (2) right before the first provider call the runner re-derives the amount and, in the transaction that sets `call_started_at`, updates the op if no call has started; (3) once `call_started_at` is set the amount is frozen — if what is owed later differs, the op fails `permanent` (`disburse_amount_changed`, alert) instead of sending the old figure. Distribution `payout` ops are fixed at commit (the run is immutable).
- **Webhooks:** `POST /api/v1/webhooks/regcf`, header `x-mock-escrow-signature: t=<unix>,v1=<hex hmac-sha256(secret, t + "." + rawBody)>`, 5-minute tolerance. Stored in `provider_events` (`provider='mock-escrow'`, unique event id) before processing; duplicate deliveries are no-ops; processing failures retry with the M1 inbox backoff. **Processing goes through the M1 inbox processor on `main` only** (M1 §3.2): every processor (inline attempt, worker, staff replay) claims the row (`processing`, `lease_until = now() + 5 min`, fresh `claim_token`) before work, and every outcome write — including the "wait for the matching row" path back to `received` — is conditional on `status = 'processing' and claim_token = <ours>`; Layer 2 adds a `regcf.*` branch to the dispatcher, never its own claim or status writes.

### 5.1 Layer 2 reconciliation and pause rule (aligned with M1 §7 on `main`)
- **Per Pool:** ledger `pool_escrow` vs provider escrow and ledger `pool_collection` vs provider collection balance. **In-flight allowance (M1 pattern):** amounts belonging to a `pool_ops` row still `sent`, or to a `regcf.*` event received less than `recon.inflightGraceMinutes` ago and not yet processed, are reported in the run's `inFlight` list and left out of the difference, so they open no break (AC-E1, finding 5). Past the grace they count.
- **Counters and liability (PR #10 review round 2, finding 7; M1 §7 "Public counters"):** each run also checks, per Pool, `raised_minor` == Σ `amount_minor` of `funded` (+ `issued` after close) investments, `investors_count` == distinct investors among them, `units_committed` == Σ Units of unexpired `reserved` + `funding` + `funded` + `issued` (a cancellation-pending `funding` investment still counts until its fund move settles or returns); a difference opens `counter_mismatch` (not money, never pauses). And the ledger **liability**: credit balance of `pool_investor_liability` == Σ `funded_received_minor` of `funded` + `refund_pending` investments + Σ open stray fund moves (§3, §3.1); a difference opens `liability_mismatch` (amount = ledger − expected; money, pausing). Expected escrow and provider escrow both include open strays, so a stray in its refund window opens no break; past `recon.maxBreakAgeBusinessDays` unconfirmed it opens `stray_fund_move_aged`.
- **Confirmation amounts:** a `pool_ops` confirmation (refund, disbursement, payout) whose provider amount differs from the op is refused by the SQL confirm function; the processor opens an `amount_mismatch` break on the Pool (refs: op id, expected, provider amount) and the event goes to the dead-letter path. It stays open until staff resolve it, as in M1.
- **Breaks** live in `pool_breaks` (never `recon_breaks`), so Layer 2 activity can't move M1's per-campaign diff or its `PAYOUT_PAUSING_KINDS` (gate condition 1). **Layer 2 pausing kinds** (`L2_PAYOUT_PAUSING_KINDS`, next to M1's in `apps/api/src/recon.ts`): `escrow_diff`, `collection_diff`, `unapplied_funding`, `liability_mismatch`, `amount_mismatch`, `stray_fund_move_aged`. **Never pausing:** `counter_mismatch`, `revenue_shortfall`, `revenue_overage`. An open one on a Pool with `|amount| > recon.materialityMinor` or older than `recon.maxBreakAgeBusinessDays` pauses **that Pool's** `disburse` and `payout` ops (left `initiated`, retried later); refunds never pause. `revenue_shortfall` and `revenue_overage` never pause: shortfall cash was never collected and overage stays in suspense, so neither can be distributed. Derived breaks (`escrow_diff`, `collection_diff`, `counter_mismatch`, `liability_mismatch`, `stray_fund_move_aged`) auto-resolve `cleared_by_run`; money-path breaks (`unapplied_funding`, `amount_mismatch`) stay open until staff resolve them, as M1's `amount_mismatch`.

## 6. Revenue ingestion and default (01b §3, §5)
- **Statement** (creator upload, labelled `SELF_REPORTED` whatever the mechanism — PR #10 review round 2, finding 9; `API_VERIFIED` stays in the check constraint for a future distributor-API feed the demo doesn't build, and no demo path writes it, seed included): refused with `pool_matured` when `period_end > matures_at`; period label, period dates, lines by revenue type; `covered_minor` = Σ lines of the Pool's revenue types; SHA-256 over canonical JSON; unique per (Pool, period).
- **Settlement line** (`BANK_RECONCILED`): created only from the provider's `deposit.settled` webhook into the Pool's collection account; reference = period label.
- **Reconciliation** (`reconcile_pool_revenue(pool, now)`, idempotent): for each unreconciled statement, matched cash = Σ settlement lines with the same reference; collected = min(cash, covered); shortfall → `pool_breaks(revenue_shortfall)`; overage stays in suspense with a `revenue_overage` break; no cash → "reported, not collected". Posts `revenue.collected:<statement>` once.
- **Default:** expected periods are consecutive `l2.periodMonths` windows from close, **stopping at maturity** — the last window ends at `matures_at` and no window starts after it (finding 8); `l2_past_due` counts only those, so a `matured` Pool can still be past due for a missed final period, and its collection state keeps working until cured or charged off. A period is past due when `period_end + l2.settlementDueDays < now` and it isn't fully collected → `AT_RISK`; at risk longer than `l2.cureDays` → `DEFAULT`; `AT_RISK` cured (no period past due any more) → `COLLECTING` automatically. Staff move `DEFAULT → REMEDIATION | CHARGED_OFF`, `REMEDIATION → CHARGED_OFF`, and **`REMEDIATION → COLLECTING`** (PR #10 review, finding 4): staff action `pool.collection_state` through `privileged()` (typed reason, audit), which `set_collection_state` allows only when `l2_past_due(pool, now)` is false — bank-reconciled cash covers every missed period — else `not_cured`. `reconcile_pool_revenue` never moves a Pool out of `REMEDIATION` or `DEFAULT`. Each transition writes an outbox notice to every holder.

## 7. Waterfall (01a §4)
- **Pure function** `allocateWaterfall()` in `packages/shared/src/waterfall.ts` (tested in shared and API). Input: run total C (= the Pool's entire `pool_revenue_unallocated` balance), split bps, holdings `[investmentId, units, capRemainingMinor]`. Fans pool F = ⌊C·fans/10000⌋; platform P = ⌊C·platform/10000⌋; creator gets the rest. F is split pro-rata by Units with **largest remainder** (ties: investment id ascending); any allocation above an investment's remaining cap is clipped and the excess re-split among uncapped holders; when every holder is capped, the remaining excess goes to the creator (`capOverflowMinor`). Σ(payouts) + creator + platform + overflow == C exactly.
- **Hash:** SHA-256 of canonical JSON of {inputs, outputs} (API side). Dry-run and commit compute the same allocation from the same DB state, so the same hash (AC-W1).
- **Maturity (PR #10 review round 2, finding 8):** the worker moves `funded → matured` (`matured_reason = 'maturity'`) once `now ≥ matures_at`, in its own step under the pool lock, whether or not a run is committed. `commit_distribution_run` accepts a Pool in `funded` **or `matured`**, so cash for periods ending on or before maturity that reconciles later is still distributed (final runs; same caps; investors at cap get nothing more and the excess goes to the creator as cap overflow). A commit never moves a Pool to `matured` by date any more; it does so only when every issued investment ends the run at its cap (`'cap_reached'`).
- **Commit** — what is checked where (PR #10 review, finding 6). **API:** `commitDistribution` recomputes the allocation and its hash from current DB state with `allocateWaterfall()` and refuses `run_stale` unless the hash equals the dry-run's. **SQL** (`commit_distribution_run(pool, label, hash, allocation, now)`) checks, under the pool lock: run total == current `pool_revenue_unallocated` balance (collected-only, AC-W3); conservation fans + creator + platform == run total, creator and platform ≥ 0 (AC-W4); platform == ⌊C·platform bps/10000⌋ and fans ≤ ⌊C·fans bps/10000⌋, with **fans == ⌊C·fans bps/10000⌋ unless every issued investment ends the run at its cap** (only then can there be cap overflow to the creator; PR #10 review round 2, finding 4); every payout is > 0, names an `issued` investment of this Pool, and keeps it within its cap (AC-W2). **SQL does not recompute the pro-rata largest-remainder split**: that the fan amount is divided by Units with largest remainder is enforced by the single shared pure function (used for dry-run and commit) and its tests (W1/W2/W4 properties in `packages/shared`, plus an API test that a committed run equals `allocateWaterfall()` of the same inputs). It then posts the allocation, creates payouts and outbox ops; unique (Pool, label) → a second commit with the same hash returns the first run, a different hash is refused (AC-W6). If every issued investment reaches its cap, the Pool becomes `matured` (`cap_reached`); maturity by date is the worker's step above.
- **Tax:** each investor payout records `tax_characterization = 'dividend'` (form `1099-DIV`, Mechanism 04 default, **counsel item L2-Q6**) and upserts `tax_1099_rows(year, investor, pool)`.
