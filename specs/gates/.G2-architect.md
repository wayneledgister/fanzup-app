# G2 Council Review: ARCHITECT seat · M1 design · 2026-10-03
**Artifacts:** `specs/02-design.md` (draft), ADR-003..006, vs `01-requirements.md` §M1 scope.
**Lens:** coherence, boundaries, data model vs access patterns, where it strains first.

| Sev | Finding | Ref |
|---|---|---|
| [BLOCKER] | **Payouts will dead-letter on a real Stripe test run.** Separate charges and transfers need *available* platform balance; test-mode card charges are pending for days unless paid with the "available balance" test card. The outbound state machine counts every provider error as an attempt and dead-letters after `outbound.maxAttempts` (≈ hours of backoff), so tranche 1 dead-letters before funds become available and exit test 8 fails. Resolved looks like: provider errors classified (retryable-and-counted / waiting-on-funds-not-counted / permanent), `balance_insufficient` waits without consuming attempts, and the runbook names the test card. | design §5 outbound state machine, §15.1; FR-PAY-004 |
| [CONCERN] | `record_tranche_released` recomputes the amount from `tranche_release_amount()` at confirmation while the payout op stored the amount at initiation. If they ever differ, the ledger posts a number that isn't what Stripe moved (FR-PAY-004 bullet 3). Pass the op amount in and assert equality. | §3.5; FR-PAY-004 |
| [CONCERN] | Public counters vs ledger (FR-PAY-009 bullet 3) have no check at M1, yet §3.5 changes how `backers_count` is computed. Add a counters-vs-ledger check to the recon run (cheap; same job). | §7; FR-PAY-009 |
| [CONCERN] | Event ordering is asserted ("processed in received order per object") but the worker drains globally oldest-first; a refund confirmation can be processed before its op is marked `sent` (webhook beats our commit). Say explicitly that confirmation applies by `outbound_op_id` metadata regardless of op state, and that `payment.succeeded` for an unknown-yet backing retries rather than going `unmatched` immediately. | §5 webhook handling |
| [CONCERN] | `fan_backings()` derives "released share" from campaign-level tranche postings — acceptable, but name it as a campaign-level ratio so M2's artist statement (FR-PAY-009 P1) doesn't reuse it per backing. | §3.5 |
| [NIT] | Migration timestamps `20261004…` sort after the existing ones — fine; keep one concern per file as listed. | §3 |
