# E1 Council — Security Seat Review

Reviewer: Security (trust boundaries, authn/authz, data protection, secrets, supply chain)
Target: /home/claude/fanzup-app

## Findings

Scope read: `supabase/migrations/*` (all three), `supabase/config.toml`, `supabase/seed.sql`, `apps/api/src/**` (app, env, db, auth, all routes, money, worker, escrow), `apps/web/src/lib/flags.ts`, `apps/web/src/lib/api.ts`, `apps/web/src/app/routes.tsx`, `apps/web/index.html`, `vercel.json`, `render.yaml`, `.github/**`, `.mcp.json`, `docs/SETUP.md`.

Overall: the money core is careful (security-definer + `search_path = ''`, EXECUTE revoked on money functions, column-level write grants, append-only ledger/audit, tagged-template SQL everywhere, Stripe signature check, test-key guard). The gaps are at the edges: what the **anon key** can read straight through PostgREST, staff authorization, MFA, abuse controls, browser hardening, and pipeline/supply-chain hygiene. Six blockers; all are small-to-medium fixes.

### S1 [BLOCKER] `artists_read` exposes KYC and payout references to anonymous users
- **Target:** `supabase/migrations/20261003000300_workflow_and_rls.sql:162` (`create policy artists_read ... using (true)`), columns defined at `20261003000100_core.sql:68-75`.
- **Problem:** RLS is row-level only. Supabase grants table-level SELECT on `public.*` to `anon`/`authenticated` by default, and the migration revokes only INSERT/UPDATE/DELETE on `artists` (line 121-122). So anyone holding the publishable anon key (it ships in the web bundle as `VITE_SUPABASE_ANON_KEY`, SETUP.md D1) can call `GET /rest/v1/artists?select=*` and receive `identity_ref` (Persona/Plaid inquiry id), `payout_account_ref` (Stripe `acct_…`), `identity_status`, `ein_verified`, `business_bank_verified`, `phone_verified` and `owner_id` for every artist, including unverified and rejected ones. The API's careful `campaign_cards` view is irrelevant; PostgREST bypasses it. KYC outcome is regulated personal data and the connected-account id is a targeting aid for payout fraud and social engineering.
- **Fix:** `revoke select on public.artists from anon, authenticated;` then `grant select (id, slug, name, genre, city, bio, tier, created_at) on public.artists to anon, authenticated;`. Expose verification as a single derived boolean (e.g. a `verified` badge column or view). Owners read their own sensitive columns through a security-definer `my_artist()` function or the API. Add an RLS test that `select identity_ref from artists` as anon fails with `42501`.

### S2 [BLOCKER] Any staff member can approve their own campaign; no separation of duties or role distinction
- **Target:** `public.review_campaign` (`…000300_workflow_and_rls.sql:52-64`), `public.is_staff` (line 5-7), `public.staff.role` (`…000100_core.sql:181-185`), `public.verify_tranche(p_tranche, p_reviewer)` (`…000200_ledger_and_money.sql:262-269`).
- **Problem:** `review_campaign` checks only `is_staff()`. A reviewer who also owns an artist (nothing prevents a staff account from creating one; seed's reviewer could) can submit and then approve their own campaign. `reviewer` and `admin` are indistinguishable everywhere. There is no rule that the reviewer is not the submitter, not the owner, and not the last person to edit. `verify_tranche` takes the reviewer id as a parameter instead of deriving it from `auth.uid()`, so whatever API wires it up can attribute verification to anyone; milestone verification directly unlocks payouts. `is_staff()` also grants every staff member read access to every backing and fulfillment (`backings_read` line 191-192), which is broader than a campaign reviewer needs.
- **Fix:** in `review_campaign`, reject when `owns_campaign(p_campaign)` or when `auth.uid()` appears in the campaign's edit/submit audit trail. Same for `verify_tranche`, and derive the actor from the verified JWT inside the function (or assert `p_reviewer` matches a passed, signed claim). Split roles: `campaign_reviewer`, `kyc_reviewer`, `payout_approver`, `admin`; payouts above a threshold need two distinct approvers. Narrow `backings_read`'s staff clause to a support role with logged access.

### S3 [BLOCKER] MFA is not enforced anywhere: no `aal2` check for staff, money or payout-account actions
- **Target:** `apps/api/src/lib/auth.ts:20-38` (verifier ignores `aal`/`amr`), `public.is_staff()` (`…000300:5-7`), `supabase/config.toml` `[auth.mfa.totp]` (enroll only), `apps/web/src/pages/auth/LogIn.tsx:9-10` (MFA step is a demo, code `000000`).
- **Problem:** PRD 01 FR-IDENTITY requires MFA; SETUP.md B3 enables TOTP enrollment. Nothing requires it. A phished password for a reviewer account can approve campaigns; for an artist it can (once wired) change the payout account; for a fan it can back campaigns with a saved card. Supabase only puts `aal` in the JWT; enforcement is the app's job.
- **Fix:** `is_staff()` should return true only when `(auth.jwt() ->> 'aal') = 'aal2'`. Add a `requireAal2()` in the API for staff routes, payout-account changes, KYC submission, and (Layer 2) any investment. Force enrollment for staff and artists before first privileged action. Add a restrictive RLS policy pattern (`as restrictive ... using ((auth.jwt()->>'aal') = 'aal2')`) on staff-only tables. Add tests.

### S4 [BLOCKER] Idempotency is check-then-act; concurrent retries create two backings and two PaymentIntents
- **Target:** `apps/api/src/routes/backings.ts:21-59`.
- **Problem:** the route reads `api_idempotency` (line 21-26), then does the work, then inserts the key with `on conflict do nothing` (line 57-58). Two requests with the same key that arrive together (double-click, mobile retry on a slow network, an attacker) both miss the lookup, both insert a backing, and both create a PaymentIntent, because the Stripe idempotency key is `payment:${backing.id}` (line 52), unique per backing. The second insert into `api_idempotency` is silently discarded, so the API returns two different `clientSecret`s for one key. That breaks the stated PRD 01a guarantee ("never creates a second backing or payment"). Separately, the perk-limit check (line 39) reads `claimed` without locking the perk, so oversell is caught only at capture by the CHECK constraint, after the card is charged, which turns into a webhook error loop (see S8).
- **Fix:** claim the key first: `insert into api_idempotency (key, user_id, request_hash, status_code) values (…, 0) on conflict do nothing returning key`. If no row comes back, return the stored response or `409 in_progress`. Do the work, then update the row. Derive the Stripe idempotency key from the scoped client key, not the new backing id. Reserve perk inventory with `select … for update` on the perk (or a reservation row with TTL) at backing time. Add a parallel-request test.

### S5 [BLOCKER] No abuse or bot controls on signup or PaymentIntent creation (card-testing exposure)
- **Target:** `apps/api/src/app.ts:25-57` (no rate limiter registered), `POST /api/v1/backings` (`routes/backings.ts:13`), `supabase/config.toml` `[auth.captcha]` commented out (~line 214), `enable_signup = true`.
- **Problem:** any confirmed account can create unlimited `pending_payment` backings, each minting a live PaymentIntent and client secret. That is the standard card-testing setup: fraudsters script small-perk checkouts to validate stolen cards, the platform pays dispute fees, and Stripe (and later the escrow partner) can terminate the account. Signup has no CAPTCHA, so making accounts is free. Pending backings never expire, so the table fills up.
- **Fix:** enable Turnstile/hCaptcha in Supabase Auth and on checkout. Add `@fastify/rate-limit` keyed on user id + IP (e.g. 5 backings/min/user, 20/hr), backed by a shared store (Upstash/Redis, since Vercel instances don't share memory). Cap concurrent `pending_payment` backings per user. Expire stale pending backings and cancel their PaymentIntents. Turn on Stripe Radar rules (velocity, CVC/ZIP required). Add Vercel WAF/Firewall rules for `/api/v1/backings`.

### S6 [BLOCKER] No security headers or CSP on a page that will take card payments and hold session tokens
- **Target:** `vercel.json` (no `headers` block for either service), `apps/web/index.html` (no CSP meta).
- **Problem:** no `Content-Security-Policy`, `Strict-Transport-Security`, `X-Frame-Options`/`frame-ancestors`, `X-Content-Type-Options`, `Referrer-Policy` or `Permissions-Policy`. supabase-js keeps the access and refresh tokens in `localStorage`, so any XSS (a third-party script, a markdown campaign `story`, a compromised npm dependency) means full account takeover. Without `frame-ancestors`, the backing page can be framed for clickjacking. PCI DSS 4.0 (6.4.3 / 11.6.1) expects script inventory and integrity on payment pages, even with Stripe Elements.
- **Fix:** add a `headers` entry in `vercel.json` with a strict CSP: `default-src 'self'`; `script-src 'self' https://js.stripe.com`; `frame-src https://js.stripe.com https://hooks.stripe.com`; `connect-src 'self' https://<ref>.supabase.co https://api.stripe.com`; `img-src 'self' data: https:`; `frame-ancestors 'none'`; `base-uri 'none'`; `form-action 'self'`. Also HSTS with preload, `nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, and a restrictive `Permissions-Policy`. Start in report-only mode with a `report-to` endpoint. Render user-authored campaign text as plain text or through a sanitizer.

### S7 [CONCERN] `profiles_read using (true)` lets anyone enumerate every user
- **Target:** `…000300_workflow_and_rls.sql:159`. Columns: `…000100_core.sql:50-57`.
- **Problem:** anon can list every profile (`id`, `handle`, `display_name`, `city`, `bio`, `created_at`). That covers fans who never chose a public presence. `id` equals the `auth.users` id, so a stable user identifier leaks. The list supports scraping, stalking ("fan in Little Rock") and correlation with backings once any backer-facing surface shows ids. `display_name` is copied from signup metadata, which users don't expect to be public.
- **Fix:** add a `is_public boolean default false` (or `visibility`) column. Anon gets column-limited SELECT only on public profiles, through a policy like `using (is_public or id = auth.uid())`. `created_at` and `city` are owner-only. Expose artist-facing data only through `artists`.

### S8 [CONCERN] Webhook handler: no event dedupe or log, no amount reconciliation, and a failure mode that loops
- **Target:** `apps/api/src/routes/webhooks.ts:116-149`; `public.record_backing_captured` (`…000200:158-186`).
- **Problem:** (a) Events aren't stored or deduped by `event.id`. Business idempotency keys cover capture and refund, but there's no forensic record of what Stripe sent, and replays within the 300 s tolerance get re-processed. (b) `record_backing_captured` books `b.amount_minor` and never compares it with `pi.amount_received`/`currency`. A mismatched or partially captured PI would be recorded at the full amount, so the ledger stops reconciling. (c) If a payment succeeds after the campaign closes or the perk sells out, the function raises → 409 → Stripe retries for 3 days, and the money is captured with no refund path. (d) `charge.refunded` takes `refunds.data[0]` (the newest, not necessarily the right one) and calls `recordRefunded` for any refund, including disputes or manual dashboard refunds on funded campaigns. Those raise, which causes another retry loop. (e) `livemode` and `account` aren't checked.
- **Fix:** add a `webhook_events(id pk, type, received_at, processed_at, error)` table, insert on receipt (`on conflict do nothing` → 200), and process asynchronously through the outbox. Assert amount and currency match the backing. Route "captured but not acceptable" to an automatic refund outbox event, not an exception. Handle `charge.dispute.*` explicitly. Reject events where `livemode` doesn't match the configured key mode.

### S9 [CONCERN] `?flags=layer2,postBeta` turns on unlaunched securities surfaces in production builds
- **Target:** `apps/web/src/lib/flags.ts:21-36` (override honoured unconditionally, persisted in `sessionStorage`).
- **Problem:** anyone can share `fanzup.com/?flags=layer2` and show investor KYC, pool investing and holdings screens before there's a funding portal, Form C, or counsel sign-off (PRD 01 §14). This is a client-only gate, so it isn't an authz hole today. But it's a regulatory exposure (it reads as an offer or solicitation of unregistered securities), and it trains the team to treat flags as access control. Once Layer 2 endpoints exist, a client flag must never be the only gate.
- **Fix:** honour URL overrides only when `import.meta.env.DEV` or `VITE_VERCEL_ENV !== 'production'`, or when signed in as staff. Tree-shake Layer 2 routes out of production bundles (`if (import.meta.env.VITE_FLAG_LAYER2 === 'true')` around the lazy imports). Enforce the same flags server-side on every Layer 2 endpoint and RLS policy.

### S10 [CONCERN] No route guards; the admin and KYC review UI ships to every visitor
- **Target:** `apps/web/src/app/routes.tsx:218-227` (`/admin`, `/admin/kyc`, `/admin/review/*`, `/ds` with no guard element), `apps/web/src/layouts/shells.tsx` (`AdminShell` has no session or role check).
- **Problem:** anyone can open `/admin/kyc` and see the identity-review workflow, its fields and decision states. Pages still render mocks, so no data leaks yet. But once wired, the only thing between a fan and the admin UI will be whatever API checks exist, and the UI gives a map of them. `/ds` (design system) is also public.
- **Fix:** add a `RequireAuth` / `RequireRole('campaign_reviewer'|…)` / `RequireAal2` wrapper element per shell, and redirect with `next=` preserved. Consider a separate admin app or origin (`admin.fanzup…`) behind SSO + IP allowlist, so the admin bundle never reaches the public CDN. Exclude `/ds` from production. Keep server-side checks as the real control (S2, S3).

### S11 [CONCERN] Dev routes and sandbox escrow fail open on configuration
- **Target:** `apps/api/src/app.ts:54-56`; `apps/api/src/env.ts:67,74` (`ESCROW_PROVIDER` defaults to `sandbox`, `NODE_ENV` defaults to `development`); `apps/api/src/routes/dev.ts:66-80`.
- **Problem:** if a deployment forgets `NODE_ENV` (Render sets it explicitly; Vercel previews or a future host may not) and leaves `ESCROW_PROVIDER` at its default, the API exposes **unauthenticated** `POST /api/v1/dev/sandbox/confirm-payment/:id` (marks any backing paid) and `/sandbox/tick?now=` (time-travel: settles any live campaign early, which can trigger refunds or funding). Separately, the production API silently runs a fake escrow if the variable is missing.
- **Fix:** fail closed. Register dev routes only when `ENABLE_DEV_ROUTES === 'true'`, and refuse to boot when that's set alongside `VERCEL_ENV === 'production'`. Make `ESCROW_PROVIDER` required (no default) outside `NODE_ENV=test`, and refuse `sandbox` when `VERCEL_ENV`/`RENDER` indicates a deployed environment. Require auth on dev routes even in dev.

### S12 [CONCERN] One high-privilege DB credential across Vercel and Render; staging is seeded with a published staff password
- **Target:** `apps/api/src/db.ts:141-156` (`set local role service_role` from the connection user); `render.yaml:22`, SETUP.md D1 (`DATABASE_URL` = the `postgres` user); `.github/workflows/db-deploy.yml:58-60,94` (`include_seed`); `supabase/seed.sql:1,23-26` (`reviewer@fanzup.test` / `FanzupDev123` is staff).
- **Problem:** the API and worker connect as `postgres`, which can do anything, including `ALTER`, `DROP` and reading `auth.users` (password hashes, emails). `asUser` relies on `set local role` per transaction: any future raw query outside `asUser`/`asService`, or one `tx.unsafe` with input, would run as `postgres`. The same credential sits in two vendors' dashboards. On staging, the seed creates a staff reviewer with a password published in the repo and docs, on an internet-reachable auth endpoint. Anyone can sign in as staff on staging, which matters as soon as staging holds real test KYC refs or a shared Stripe account.
- **Fix:** create a dedicated `fanzup_api` login role that is `NOINHERIT` and a member only of `anon`, `authenticated` and `service_role` (not superuser, not owner of schemas). Use separate roles and credentials for the Vercel API and the Render worker, and rotate them on a schedule. Use Stripe **restricted keys** scoped to PaymentIntents, Refunds and Transfers. For staging seeds, generate random passwords per environment (or use magic link only) and never seed a staff row; grant staff by a manual, audited step.

### S13 [CONCERN] Audit trail and logging aren't enterprise-grade: no request context, no access logging, partial redaction
- **Target:** `public.audit_events` (`…000200:79-88`); Fastify logger `redact` (`apps/api/src/app.ts:27`); `drainOutbox` stores `String(e)` in `outbox.last_error` (`apps/api/src/money.ts:80`); `server.ts:222-227`.
- **Problem:** audit rows have no IP, user agent, request id, session id or `aal`, and system actions have `actor_id = null`. Staff reads of backings, KYC or (later) addresses aren't logged at all. Redaction covers only `authorization`/`cookie`, not `stripe-signature`, `idempotency-key`, query strings, or response bodies that carry `clientSecret`. Raw provider errors (which can include PII or account ids) go into a table and into stdout. The misconfigured/startup handlers return config issue text and error codes to the public internet (`server.ts:179-186, 227`). Append-only is enforced by trigger, but `service_role`/`postgres` can still disable triggers, so there's no external tamper evidence.
- **Fix:** add `request_id`, `ip`, `ua`, `aal` and `session_id` to `audit_events` (set via `set_config` in `asUser`/`asService`). Log every staff read of sensitive records. Extend `redact` (`req.headers["stripe-signature"]`, `req.headers["idempotency-key"]`, `*.clientSecret`, `*.email`). Ship logs and audit to an append-only sink (Logtail/Datadog with retention lock, or S3 Object Lock). Return only a generic 503 publicly and put details behind a health token.

### S14 [CONCERN] CI supply-chain controls are thin
- **Target:** `.github/workflows/ci.yml` (no `permissions:` block; actions pinned by tag `@v7`/`@v6`); `.github/workflows/db-deploy.yml:91,120` (`supabase/setup-cli@v3` with `version: latest`); `.github/` (no CODEOWNERS, no CodeQL/SAST, no secret scanning, no dependency review); `render.yaml:14` (autoDeploy).
- **Good:** `dependabot.yml` covers npm and actions. `--frozen-lockfile` is used everywhere. pnpm 10 blocks dependency lifecycle scripts by default. The prod migration environment has required reviewers.
- **Problem:** the default `GITHUB_TOKEN` scope applies to CI on PRs. Tag-pinned third-party actions (`pnpm/action-setup`, `supabase/setup-cli`) can be retargeted (tj-actions/changed-files, 2025). `version: latest` means the migration CLI that touches production changes without review. There's no static analysis, no secret scanning push protection, no `pnpm audit`/OSV gate, no SBOM, no provenance. And no CODEOWNERS requiring founder review on `supabase/migrations/**`, `apps/api/src/money.ts`, or `apps/api/src/routes/**`.
- **Fix:** add `permissions: contents: read` at the top of `ci.yml`. Pin every action to a full commit SHA (Dependabot keeps SHAs updated). Pin the Supabase CLI version. Add CodeQL (JS/TS), `actions/dependency-review-action`, gitleaks or GitHub secret scanning with push protection, `pnpm audit --prod --audit-level high` (or osv-scanner), and SBOM generation (CycloneDX). Add CODEOWNERS plus branch protection (required checks, signed commits, no force-push on `main`). Add a pgTAP/RLS regression job that asserts anon column grants (S1).

### S15 [CONCERN] No account deletion or data export, and the FK design blocks deletion
- **Target:** `artists.owner_id … on delete restrict` and `backings.backer_id … on delete restrict` (`…000100_core.sql:61,149`); `profiles … on delete cascade` from `auth.users` (line 51); no API endpoints for export or deletion; `docs/CONSOLIDATION.md:134` (a "14-day account-deletion grace" is promised in UI copy).
- **Problem:** deleting an auth user who has backed anything or owns an artist fails with an FK error, so a CCPA/state-privacy deletion request can't be honoured without manual SQL. Financial records must be kept (BSA/tax, and Reg CF later), so this needs pseudonymisation rather than deletion. Nothing exports a user's data (CCPA right to know). The UI promises a grace period that no backend implements.
- **Fix:** design a `request_account_deletion()` flow: mark the account, apply the grace period, then a worker job revokes sessions, scrubs profile and display fields, replaces `auth.users` email with a tombstone, keeps ledger and backing rows linked to a pseudonymous id, and writes an audit record. Add `GET /v1/me/export` (JSON of profile, backings, fulfillments, audit about the user). Write a retention schedule (what's kept, how long, legal basis).

### S16 [CONCERN] Shipping address PII for physical perks has no design yet, and it's the most sensitive data artists will touch
- **Target:** `public.perks.kind = 'physical'`, `ships_to` (`…000100_core.sql:132-137`); `public.fulfillments` (line 162-168) has no address; `fulfillments_artist_update` (`…000300:197-199`); `.E1-critic.md` asks for address capture at checkout.
- **Problem:** physical perks are live in the seed, but there's nowhere to store a recipient address. The obvious quick fix (add `address jsonb` to `backings` or `fulfillments`) would make it readable by the artist and every staff member through the existing RLS, retained forever, with no access log. Artists are third parties to the fan; handing them home addresses is a data-sharing event that needs disclosure and minimisation.
- **Fix:** store addresses in a separate `shipping_addresses` table with no anon or authenticated SELECT grant. Encrypt with pgsodium/Vault or app-level envelope encryption. Reveal to the artist only through a security-definer function that requires campaign `funded`, perk `kind='physical'`, artist `aal2`, and writes an audit row. Offer a CSV export with a short-lived signed URL. Purge 90 days after `Delivered`. Disclose sharing in the privacy policy and at checkout.

### S17 [NIT] JWT verification checks audience but not issuer, and revocation lags up to an hour
- **Target:** `apps/api/src/lib/auth.ts:26-31`; `supabase/config.toml:166` (`jwt_expiry = 3600`).
- **Problem:** no `issuer` option, so with a shared HS256 secret any token from another project or environment that shares the secret is accepted (staging tokens on prod if secrets are reused). Both HS256 and JWKS paths stay live when both are configured. Banned or signed-out users keep API access until the token expires, which matters for staff offboarding.
- **Fix:** pass `issuer: ${SUPABASE_URL}/auth/v1` and pin `algorithms`. Migrate to asymmetric keys only and drop `SUPABASE_JWT_SECRET`. Shorten `jwt_expiry` to 15 min for staff, or check `session_id` against `auth.sessions` on privileged routes.

### S18 [NIT] Function hygiene: mutable `search_path` on non-definer functions; CORS broader than needed
- **Target:** `public.touch_updated_at`, `public.enforce_campaign_transition`, `public.ledger_check_balanced`, `public.ledger_append_only`, `public.campaign_is_public` (no `set search_path`); `apps/api/src/app.ts:31` (`credentials: true`).
- **Problem:** Supabase's linter flags `function_search_path_mutable`. These run as the invoker, so the risk is low, but the ledger invariant trigger resolving `public.ledger_entries` via the caller's path is the kind of thing an auditor will flag. CORS with `credentials: true` isn't needed: the API is same-origin and uses bearer tokens, not cookies.
- **Fix:** add `set search_path = ''` to every function and run `supabase db lint` / the Advisors in CI. In production, drop CORS or set `credentials: false` with an explicit allowlist.

## Enterprise security baseline
Controls I'd require before calling FanZuP "enterprise-grade" for money + identity + (later) securities.

**Identity & access**
- [ ] MFA (TOTP/WebAuthn) mandatory for staff and artists; `aal2` enforced in DB (`is_staff`) and API for money, payout, KYC, review actions
- [ ] Passkeys offered to fans; step-up re-auth for payout-account changes and email changes
- [ ] Granular staff roles (campaign_reviewer, kyc_reviewer, payout_approver, support, admin) with least privilege
- [ ] Separation of duties: no self-review; two-person approval for payouts above threshold and for role grants
- [ ] Staff on SSO (Google Workspace/Okta) with quarterly access reviews and same-day offboarding (session revocation)
- [ ] JWT verification pins issuer, audience and algorithm; asymmetric keys only; short staff token lifetime

**Data protection**
- [ ] Column-level SELECT grants on every table with sensitive columns; anon sees an explicit allowlist only
- [ ] RLS regression suite (pgTAP) asserting anon/authenticated column and row visibility, run in CI
- [ ] Data classification register (public / internal / PII / KYC / financial) mapped to tables and columns
- [ ] Shipping addresses and any PII encrypted at rest (Vault/pgsodium), reveal-on-need with audit, retention purge
- [ ] KYC documents never stored; only vendor refs, readable by owner + kyc_reviewer
- [ ] Account deletion (pseudonymisation preserving ledger), data export, documented retention schedule
- [ ] Privacy policy and processor list (Supabase, Vercel, Render, Stripe, Persona) with DPAs signed

**Application security**
- [ ] Strict CSP, HSTS preload, frame-ancestors none, nosniff, Referrer-Policy, Permissions-Policy
- [ ] Rate limiting (shared store) on auth, backing, and all write endpoints; CAPTCHA on signup and checkout
- [ ] Atomic idempotency (claim-first) on every money-moving endpoint; parallel-request tests
- [ ] Webhook event store with dedupe, amount/currency/livemode reconciliation, async processing, dispute handling
