# G1 Council — Security Seat · FanZuP v2 requirements

**Seat:** Security (authn/authz, data protection, trust boundaries, abuse, secrets) · **Date:** 2026-10-03 · **Tier:** Enterprise
**Artifacts reviewed:** `specs/00-brief.md`, `specs/01-requirements.md`
**Upstream checked against:** `gates/E1-enterprise-readiness.md` (B1–B12, C1–C17), `gates/.E1-security.md` (S1–S18 + Enterprise security baseline), repo at `a165610` (`packages/shared/src/policy.ts`, migrations, `apps/api`).

**Summary.** The conversion of E1 security blockers is mostly faithful. S1 (column grants + CI drift test, NFR-SEC-01), S3 (server-enforced step-up, FR-ID-002), S4 (claim-first idempotency + parallel test, FR-PAY-006), S5 (shared-store rate limits + bot challenge on backing, FR-TAX-004), S6 (CSP/HSTS with report-only ramp, NFR-SEC-03), S11 (fail-closed, NFR-SEC-04), S12 (per-runtime roles, no seeded staff, NFR-SEC-05/07) and S14 (CI supply chain, NFR-SEC-09) are now testable requirements. Two problems block the gate. The S2 separation-of-duties fix lost its central control and now contradicts itself. The spec also adds a P0 file-upload surface (campaign media, milestone evidence, dispute evidence, export files) with no access-control or content-safety requirement. Most of the remaining gaps sit in the new growth surfaces (comments, updates, embeds, referral links, QR tickets, push, exports). Each of these adds attack surface, but none has its own authz or data-protection line, and the security baseline items that would have covered them (sanitised rendering, rate limits on all write endpoints, data-classification register, log redaction, auth-anomaly alerting) were dropped or narrowed when the baseline became NFR-SEC.

## Findings

| # | Sev | Finding | Ref |
|---|---|---|---|
| 1 | [BLOCKER] | **The separation-of-duties fix for E1 B7/S2 is incomplete and self-contradictory.** (a) The core S2 defect was `verify_tranche` trusting a caller-supplied reviewer id. No requirement says that the acting staff identity (and its `aal`) is taken from the verified session inside the money/approval function and never from a parameter. "Every transition is audited with actor" (FR-CMP-002) does not stop the actor from being forged. (b) NFR-COMP-17 requires evidence plus **two distinct approvers to verify** a tranche above a threshold. FR-PAY-005 says that once a tranche is verified its release is scheduled "with no further manual step", and FR-ID-003 says "releases … above policy thresholds need two distinct approvers". A test can't satisfy all three: either verification is dual-control and release is automatic, or release is dual-control and FR-PAY-005 is wrong. (c) "Owns or is linked to" (FR-ID-003, NFR-COMP-17) is never defined. It should at least cover the owner, team members, the submitter, the last editor (S2), and accounts linked by the FR-TAX-004 signals. (d) Nothing narrows staff row access (S2: `is_staff()` reads every backing); FR-ADM-002 audits views but doesn't scope them by role. **Resolve:** add an AC to FR-ID-003 ("acting staff id and aal derived server-side from the session; any function accepting an actor id is rejected in review/CI"); pick one dual-control point for tranches and align FR-PAY-005, FR-ID-003 and NFR-COMP-17; define "linked"; add per-role row scoping to NFR-SEC-01. | FR-ID-003, FR-PAY-005, FR-CMP-002, NFR-COMP-17; E1 B7; Sec S2 |
| 2 | [BLOCKER] | **P0 file uploads and downloadable files have no security requirement.** The spec makes users upload and download files on P0 paths: campaign media (FR-CMP-001), milestone evidence "files" that directly unlock payouts (FR-PAY-005), and dispute evidence (FR-DSP-002). P1 adds update images (FR-COM-001), fulfillment export files (FR-FUL-001), DSAR archives (FR-PRV-002) and receipts (FR-BCK-005). NFR-SEC-01 covers *tables*, not object storage, so nothing requires: bucket-level access policy (private by default; backers-only update media actually private, not a guessable public URL); signed URLs with a stated maximum TTL ("a link that expires" has no bound); content-type allowlist, size limits and server-side type sniffing; SVG/HTML never served inline from the app origin (stored XSS against a CSP whose `img-src` allows `https:`); malware scanning of evidence that staff reviewers open; EXIF/GPS stripping of artist and fan photos; aal2 + audit on fulfillment and DSAR export downloads. Milestone evidence is the input to a money release. If it can be swapped or replayed, a forged verification follows. **Resolve:** add an NFR-SEC "uploads and object storage" requirement with these ACs and cite it from each FR above. | FR-CMP-001, FR-PAY-005, FR-DSP-002, FR-COM-001, FR-FUL-001, FR-PRV-002, FR-BCK-005; NFR-SEC-01, NFR-SEC-03 |
| 3 | [CONCERN] | **NFR-SEC-01's read-visibility test covers tables only.** Supabase exposes views, RPC functions (EXECUTE defaults to PUBLIC on new functions) and Realtime channels, and the spec adds new readable data: follows (FR-GRO-004 promises "follower counts, not identities, unless the fan opts in"), opt-in backer wall (FR-GRO-005), referral attribution (FR-GRO-003), backers-only updates (FR-COM-001), comment reports, notification inbox (FR-NTF-002), push subscriptions (FR-NTF-003). These privacy promises are UI statements with no matching data-layer control. **Condition:** extend NFR-SEC-01 and its CI test to views, function EXECUTE grants, Realtime/broadcast channels and storage. Add a data-layer AC to FR-GRO-004, FR-GRO-005 and FR-COM-001. | NFR-SEC-01, NFR-SEC-02; FR-GRO-003/004/005, FR-COM-001, FR-NTF-002/003; E1 C3 |
| 4 | [CONCERN] | **Abuse controls were narrowed from "all write endpoints" to backing only.** The baseline required shared-store rate limits on auth, backing and *all* write endpoints. FR-TAX-004 covers backing, sign-up and checkout. Uncovered: sign-in, magic-link and password-reset sends (credential stuffing, email bombing, and sender reputation for transactional mail), passkey/MFA attempts, comment/report/follow/notify-me writes (FR-COM-002, FR-GRO-004, FR-CMP-005), referral-link minting, DSAR export requests (FR-PRV-002 runs heavy jobs), and the dynamic social-card renderer (FR-GRO-001, an unauthenticated CPU path). There's no lockout/back-off AC beyond "locked-account state handled" (FR-ID-001). **Condition:** add an NFR-SEC rate-limit/abuse requirement covering every unauthenticated or write route, with limits in policy, plus an alert on spikes. | FR-TAX-004, FR-ID-001, FR-COM-002, FR-GRO-001/003/004, FR-CMP-005, FR-PRV-002; E1 B8; Sec S5, baseline |
| 5 | [CONCERN] | **Account-takeover-to-payout path is only half closed.** FR-ID-002 requires MFA and recent re-auth to change a payout account, and FR-NTF-001 sends a security email. But FR-PAY-005 auto-releases within 1 business day, so an attacker who passes step-up (SIM-swap, session theft, phished TOTP) can redirect a tranche before the artist reads the email. Nothing requires a cooling-off hold on releases after a payout-destination or email change, or staff review of that combination. The baseline's alerting on "auth anomalies" and "unusual payout patterns" was dropped: NFR-OPS-11 lists neither. **Condition:** add an AC (FR-ID-004 or FR-PAY-005): payout-destination change ⇒ releases held for a policy window and the change confirmed out-of-band. Add auth-anomaly and payout-change-then-release signals to NFR-OPS-11. | FR-ID-002, FR-ID-004, FR-PAY-005, FR-NTF-001, NFR-OPS-11; Sec baseline "Logging, monitoring" |
| 6 | [CONCERN] | **User-authored content: safe rendering is required for comments only, and the embed widget conflicts with the CSP.** FR-COM-002 says comments render safely. Nothing says the same for the campaign story, use of funds and risks (FR-CMP-001/003, P0, the S6 example), updates (FR-COM-001), FAQ entries, artist bio, survey answers shown to artists (FR-FUL-001), social-card text (FR-GRO-001) or **emails that carry artist update content** (FR-COM-001 → FR-NTF). That last one is a FanZuP-branded phishing channel to every backer, and nothing requires link handling or a template boundary. The embeddable progress widget (FR-GRO-002) can't work under NFR-SEC-03's `frame-ancestors none`. No requirement defines its separate origin, a read-only payload with no session, a per-campaign kill switch, or allowed-host policy. **Condition:** add a baseline NFR-SEC "all user-authored content is sanitised/encoded on every output channel (web, email, OG image, embed)" with output-encoding tests. Add an embed AC to FR-GRO-002 that defines its own origin and frame policy. | FR-CMP-001/003, FR-COM-001/002, FR-FUL-001, FR-GRO-001/002, NFR-SEC-03; Sec S6, baseline "Sanitised rendering" |
| 7 | [CONCERN] | **Several FRs collect personal data with no stated purpose or retention, and the data-classification register was dropped.** Examples: device and address signals for linked-account detection (FR-TAX-004); viewer events for the funnel (FR-ANL-001; "no individual data shown" says nothing about what is *stored*); referral attribution per fan (FR-GRO-003); artist-defined survey fields (FR-FUL-001; an artist can ask for phone, DOB or anything else, unbounded); raw provider event payloads that include cardholder name, email and address (FR-PAY-002); message logs (FR-NTF-001); IP/UA on every acceptance and audit row (FR-PRV-001, NFR-COMP-11); push endpoints (FR-NTF-003). NFR-SEC-08 encrypts only "PII beyond email" and sets a purge only for addresses. The retention schedule (NFR-COMP-13) is P1, while P0 features already collect these. The idempotency-row TTL (Comp F19) didn't survive either. **Condition:** add a P0 NFR-SEC data-classification register (class → tables/columns/buckets → purpose → retention → who can read). Constrain survey fields to a typed allowlist. Each collecting FR cites its class. | FR-TAX-004, FR-ANL-001, FR-GRO-003, FR-FUL-001, FR-PAY-002, FR-NTF-001/003, FR-PRV-001; NFR-SEC-08, NFR-COMP-13; Sec baseline "Data classification register" |
| 8 | [CONCERN] | **Referral links can de-anonymise private fans.** FR-GRO-003 gives each fan a personal link and shows artists "backers and amount by source". FR-PRV-004 makes fan profiles private by default. The spec doesn't say the link token is opaque and unguessable (not a handle or user id), that a landing page never displays "referred by <fan>", or whether "by source" can resolve to a named fan and the amounts they drove. If it can, the artist learns identities and spend patterns that FR-PRV-004 and FR-GRO-004 promise to hide. **Condition:** add ACs: opaque, revocable tokens; artist sees per-fan attribution only for fans who opted into a public profile, otherwise aggregated; tokens are not usable for enumeration. | FR-GRO-003, FR-PRV-004, FR-GRO-004 |
| 9 | [CONCERN] | **Log redaction and log integrity were dropped from S13.** NFR-OPS-04 sends API, worker *and web* errors to an error tracker, and FR-PAY-002 stores raw provider events. No requirement says logs, traces and error events redact auth headers, `stripe-signature`, idempotency keys, client secrets, emails, addresses or tokens. The browser error tracker would capture URLs carrying magic-link and reset tokens. Log retention and tamper-evidence are in the baseline but only audit rows got them (NFR-COMP-12). NFR-SEC-04 covers public error bodies only. **Condition:** add an NFR-SEC: one redaction list applied to logs, traces, error tracker (server and browser, including URL query/fragment scrubbing) and stored provider payloads; logs shipped to retention-locked storage for ≥ 1 year. | NFR-OPS-04, FR-PAY-002, NFR-SEC-04, NFR-COMP-12; Sec S13, baseline |
| 10 | [CONCERN] | **Threat-model scope and pen-test timing are weaker than the baseline.** NFR-SEC-10 scopes the threat model to backing, payout, milestone verification, staff tools and identity. It omits every new surface: uploads, comments/moderation, embeds, referral links, exports, push, QR tickets, the social-card renderer. The pen-test priority is muddled: "P1 … before real money if Beta takes live money". The document defines P0 as "required before a beta that takes real money", and FR-PAY-008 controls when that happens, so the conditional adds nothing and reads as a softening of "before real money". **Condition:** list all surfaces in NFR-SEC-10 and make the pen test P0, gated with FR-PAY-008's live-key switch. | NFR-SEC-10, FR-PAY-008; Sec baseline "Supply chain & SDLC" |
| 11 | [CONCERN] | **QR show tickets lack a security model.** "Codes can't be duplicated or forged" can't be tested as written. The open questions: signed tokens (whose key, does it rotate)? Revocation when the backing is refunded, cancelled (FR-BCK-003, FR-FUL-003) or charged back (FR-DSP-002), given that scanning "works offline"? Who may scan (artist account only, or delegated door staff with a scoped, expiring credential)? Is the emailed code a bearer token, and can a fan re-issue it if it's leaked? P2, so this is a tracked condition before FR-FUL-004 is designed, not a gate stop. **Condition:** rewrite the ACs to cover signature, revocation-list sync on scanner open, scoped scanner credential, and single-use enforcement on reconnect. | FR-FUL-004, FR-BCK-003, FR-DSP-002 |
| 12 | [NIT] | **Small conversion losses.** NFR-SEC-06 pins issuer, audience and algorithm but drops "asymmetric keys only; remove the shared HS256 secret" (S17). Staff sessions get a 15-minute idle timeout, but there's no maximum absolute lifetime. Staff SSO and the separate admin origin are P1 (FR-ID-005), so the Beta staff console ships in the public bundle. That's acceptable given server-side checks, but it should be said explicitly. Web push payloads (FR-NTF-003) should carry no money amounts or PII, since they show on lock screens. | NFR-SEC-06, FR-ID-005, FR-NTF-003; Sec S10, S17 |
